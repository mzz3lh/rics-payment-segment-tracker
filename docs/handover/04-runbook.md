# Operational runbook: RICS Payment Segment Tracker

## Components and load order

The solution so far has seventeen loads (MOD-002 to MOD-008 and MOD-010 to MOD-012) and two read-only profiles (MOD-001):

| Component | What it does | Parameters |
|---|---|---|
| Layercake.usp_load_brnz_subs_invoice | Load: brings Layercake.brnz_subs_invoice up to date with Subs.tblSubsInvoices | None |
| Layercake.usp_load_brnz_subs_invoice_line | Load: brings Layercake.brnz_subs_invoice_line up to date with the in-scope rows of synapse_fo.CUSTTRANS_RICS | None |
| Layercake.usp_load_brnz_corporate_subscription | Load: brings Layercake.brnz_corporate_subscription up to date with Subs.vwCorpSubscriptions | None |
| Layercake.usp_load_brnz_concession | Load: brings Layercake.brnz_concession up to date with the concession reference, CE.vwConcessionType | None |
| Layercake.usp_load_dim_payment_method | Load: brings Layercake.dim_payment_method into step with the payment method list, Layercake.silv_ref_payment_method | None |
| Layercake.usp_load_dim_payer_type | Load: brings Layercake.dim_payer_type into step with the payer type list, Layercake.silv_ref_payer_type | None |
| Layercake.usp_load_silv_ref_invoice_line_type | Load: adds new item codes from Layercake.brnz_subs_invoice_line to the line-type mapping, Layercake.silv_ref_invoice_line_type, as 'unmapped' | None |
| Layercake.usp_load_silv_ref_currency | Load: adds new currency codes from Layercake.brnz_subs_invoice to the currency list, Layercake.silv_ref_currency | None |
| Layercake.usp_load_dim_currency | Load: brings Layercake.dim_currency into step with the currency list | None |
| Layercake.usp_load_silv_ref_concession_type | Load: adds new concession types from Layercake.brnz_concession to the concession type list, Layercake.silv_ref_concession_type, and updates the name, item code and flags of listed types that changed | None |
| Layercake.usp_load_dim_concession_type | Load: brings Layercake.dim_concession_type into step with the concession type list | None |

| Layercake.usp_load_silv_data_anomaly_invoice | Load: brings the six invoice anomaly types in Layercake.silv_data_anomaly up to date | Still to be confirmed |

| Layercake.usp_load_fact_membership_events_segments | Load: copies those columns to Layercake.fact_membership_events and checks that silver and gold agree | Still to be confirmed |
| Layercake.usp_profile_custtrans_grain | Profile: the grain of synapse_fo.CUSTTRANS_RICS, for open question Q-021 | None |

The payment method and payer type lists, the mapping function Layercake.fn_map_payment_method and the eligible-invoice view Layercake.vw_silv_eligible_invoice are not run on their own: the lists are put in place by their migrations, the function is used inside the attributes load, and the view inside the attributes load, the event amount load and the invoice anomaly load.

MOD-008 also changes the Phase 1 anomaly load, Layercake.usp_load_silv_data_anomaly, which still runs as part of the Phase 1 run; it now leaves the segment and invoice anomaly types alone (see the Architecture and data model document).

MOD-009 adds no load. It removes the payment_source column from the Phase 1 table Layercake.silv_payment_events. That table's Phase 1 load, Layercake.usp_load_silv_payment_events, still runs as part of the Phase 1 run and is unchanged, because it never wrote the column (see the Architecture and data model document).

MOD-017 adds no load either. It changes the Phase 1 load Layercake.usp_load_brnz_subs_status, which now also fills the two new columns of Layercake.brnz_subs_status, 'Inv Total Amount' and 'Retired Concession'. It still runs in the bronze step of the Phase 1 run (Layercake.usp_load_bronze, called by Layercake.usp_run_daily_load), before the Phase 1 silver loads, and still takes one optional parameter, a run id. It reads only its source, Subs.vwSubsMemberStatuses, so it depends on no other load. Its Retired Concession column is read by the derived retirement date (MOD-018), and its Inv Total Amount column by the event amount load (MOD-010). Because this load runs inside the Phase 1 run, before the Phase 1 silver loads and before the new loads that run after the Phase 1 run, the columns are always current by then.

MOD-018 adds no load either. The derived retirement date view, Layercake.vw_silv_derived_retirement_date, is not run on its own: the Phase 1 member base load, Layercake.usp_load_silv_member_base, reads it. MOD-018 changes that load and the Phase 1 events load, Layercake.usp_load_silv_membership_events. Both still run in the silver step of the Phase 1 run (Layercake.usp_load_silver, called by Layercake.usp_run_daily_load), whose order the design keeps: the member base first, then the membership events, the member profile, the daily counts and the annual rate base, which all use the retirement date it writes. The view reads brnz_subs_status, which the member status load fills in the bronze step of the same run, so the derived date is always current before any Phase 1 status is set. Nothing about this order needs to be set up separately.

Eleven loads read the output of another load, so they must run after it:

1. usp_load_silv_ref_currency reads brnz_subs_invoice, so it runs after usp_load_brnz_subs_invoice.
2. usp_load_dim_currency reads the currency list, so it runs after usp_load_silv_ref_currency.
3. usp_load_silv_ref_invoice_line_type reads brnz_subs_invoice_line, so it runs after usp_load_brnz_subs_invoice_line.
4. usp_load_silv_ref_concession_type reads brnz_concession, so it runs after usp_load_brnz_concession.
5. usp_load_dim_concession_type reads the concession type list, so it runs after usp_load_silv_ref_concession_type.
6. usp_load_silv_member_year_attributes reads brnz_subs_invoice, brnz_subs_invoice_line, the line-type mapping, brnz_corporate_subscription, brnz_concession and the concession type list, so it runs after usp_load_brnz_subs_invoice, usp_load_brnz_subs_invoice_line, usp_load_silv_ref_invoice_line_type, usp_load_brnz_corporate_subscription, usp_load_brnz_concession and usp_load_silv_ref_concession_type. It also reads the Phase 1 tables silv_membership_events and silv_payment_events, so it runs after the Phase 1 run.
7. usp_load_silv_data_anomaly_segment reads each contact-year's segment invoice from the member-year attributes, so it runs after usp_load_silv_member_year_attributes. It also reads the bronze invoice, invoice line and corporate subscription tables and the concession type list, which the attributes load already follows.
8. usp_load_silv_event_amount reads, through the eligible-invoice view, brnz_subs_invoice, brnz_subs_invoice_line and the line-type mapping, so it runs after usp_load_brnz_subs_invoice, usp_load_brnz_subs_invoice_line and usp_load_silv_ref_invoice_line_type. It also reads the Phase 1 tables silv_membership_events and silv_payment_events, and brnz_subs_status, which the Phase 1 run fills, so it runs after the Phase 1 run. It does not read the member-year attributes.
9. usp_load_silv_data_anomaly_invoice reads the pairing of events with invoices in the event amounts table, so it runs after usp_load_silv_event_amount. It also reads brnz_subs_invoice, brnz_subs_invoice_line and the line-type mapping, which the event amount load already follows, and the Phase 1 Campaign Year table, ref_campaign_year_config.
10. usp_load_silv_membership_events_segments reads the member-year attributes and the event amounts table, so it runs after usp_load_silv_member_year_attributes and usp_load_silv_event_amount. It also reads the Phase 1 tables silv_membership_events and silv_payment_events, so it runs after the Phase 1 run.
11. usp_load_fact_membership_events_segments copies the columns that the silver event column load writes, so it runs after usp_load_silv_membership_events_segments. It also reads the Phase 1 gold fact, fact_membership_events, which the Phase 1 run loads, so it runs after the Phase 1 run.

The other loads do not read another load's table: the line load takes its list of invoices directly from Subs.tblSubsInvoices, the corporate subscription and concession bronze loads read only their sources, and the payment method and payer type dimension loads read only their lists, which no load writes. In the design, all the loads run as part of one run procedure, Layercake.usp_run_payment_segments, which runs every new load in dependency order after the Phase 1 run, with the event amounts after the member-year attributes and before the segment and invoice anomalies, and the silver event columns and then the gold fact columns last. That run procedure comes in a later module (MOD-016).

The four dimensions are not filled by their migrations. Each stays empty until its load is first run (for the currency and concession type dimensions, after their list loads). Until the run procedure is delivered, the list loads, the four dimension loads, the attributes load, the segment anomaly load, the event amount load, the invoice anomaly load and the two event column loads are run by hand (see Deployment and rollback).

The two profiles do not depend on each other and can be run in either order. They are intended to be run on real data before the invoice build, so their results can answer Q-021 and Q-027 (see Known limitations).

## Scheduling

The loads are designed to run after the Phase 1 run, through the run procedure that a person schedules once it is delivered (MOD-016). The schedule itself (when and how often the run happens) is still to be confirmed.

The member status load changed by MOD-017 needs no schedule of its own: it runs whenever the Phase 1 run (Layercake.usp_run_daily_load) runs, as before. The same applies to the member base and events loads changed by MOD-018.

The one-off daily rebuild after MIG-0013 is deployed (see Deployment and rollback) is not part of any schedule. It recomputes the daily counts from 1 October 2020, the one heavy step the amended design adds, so the design has a person run it once, outside the daily window. When it is to be run is still to be confirmed.

The attributes load needs no argument on a scheduled run: its as-of date defaults to the day it runs, so the current Campaign Year moves on by itself when a new Campaign Year starts, as long as Layercake.ref_campaign_year_config has a row covering the date (see Error handling).

The profiles are not part of any scheduled load. Mike runs them on real data when the answers are needed and brings the results back as answers to the open questions.

## Monitoring

Each load records one row per run in the load log, Layercake.etl_run_log, with:

- its outcome: 'Success' or 'Failed';
- the numbers of rows inserted, updated and deleted (for the bronze loads, marked as deleted) in its table;
- for a failed run, the error message.

A second run on unchanged data records 0 inserted, 0 updated and 0 deleted. Each bronze load also checks that its table's live rows equal the source rows in scope (RULE-005); a mismatch fails the run, so it shows as 'Failed' in the log. In the corporate subscription and concession bronze loads, making a deleted row live again is counted as an update, and in the concession bronze load a change only in letter case or trailing spaces is also counted as one update. The dimension loads never remove rows, so their deleted count is always 0; in the concession type dimension, a change only in a flag counts as one update. The line-type mapping and currency list loads only add rows, so they record only rows inserted. The concession type list load records rows inserted (new types) and rows updated (types whose name, item code or flags changed).

The attributes load records its run under the layer 'silver' and the step 'silv_member_year_attributes', with the contact-years it added, updated and deleted. A change only in the letter case of a scheme number counts as an update.

The segment anomaly load records the anomaly cases it added (inserted), those whose detail it rewrote (updated) and those it removed because they no longer apply (deleted). The cases themselves are the rows of the four segment anomaly types in Layercake.silv_data_anomaly (see the Architecture and data model document).

The invoice anomaly load records its run in the same way: the cases it added (inserted), those whose detail it rewrote (updated), for example when a paired invoice's number changes, and those it removed because they no longer apply (deleted), for example when a corrected invoice is now paired with its event. The cases themselves are the rows of the six invoice anomaly types in Layercake.silv_data_anomaly (see the Architecture and data model document).

The event amount load records its run under the layer 'silver' and the step 'silv_event_amount', with the events it added, updated and deleted. Its first run adds one row for every Join, Renewal and Readmission. After that, an event whose amount, amount status or paired invoice changes counts as an update, as does a change only in the letter case of its contact number or event type, and a row for an event that has left the event table counts as a deletion. Each row's load_id points to the load log entry of the run that last wrote it.

The two event column loads never add or remove rows, so they record only the events they updated; their inserted and deleted counts are always 0. Only events whose values differ from what they held before are updated, so a second run on unchanged data records 0 updated. A change only in the letter case of an amount status counts as an update.

The member status load records its run under the layer 'bronze' and the step 'brnz_subs_status', as in Phase 1. Its first run after MIG-0012 is deployed updates every live row once, to fill the two new columns, so that run records as many rows updated as the table has live rows; this is expected. After that, a run on unchanged data records 0 inserted, 0 updated and 0 deleted. A change in either new column counts as an update, including a change only in the letter case or trailing spaces of Retired Concession, and so does making a deleted row live again.

The member base load changed by MOD-018 records its run under the layer 'silver' and the step 'silv_member_base', as in Phase 1. Because it works its whole table out again on every run, it records every row as inserted and the rows it replaced as deleted, even on unchanged data; this is how Phase 1 has always logged it.

The first Phase 1 run after MIG-0013 is deployed changes many members' retirement dates. The member profile load then records that past daily counts are affected, in Layercake.etl_daily_count_pending_rebuild: an open row (one with no applied time) with source 'member_profile' and, as affected_from, the earliest already-loaded day the change affects, never earlier than 1 October 2020. Such a row is written only when some day already loaded is affected, and there is at most one open row per source, holding the earliest date seen. The row is the signal that past daily counts still need the one-off rebuild (see Deployment and rollback); the daily run does not rebuild them by itself. The rebuild marks the row as applied.

New rows in the line-type mapping arrive as 'unmapped'. A run of usp_load_silv_ref_invoice_line_type that records rows inserted means new item codes have appeared that a person needs to map by hand (see Known limitations).

The profiles do not record a run in the load log, because they load nothing. Their output is the result set they return, which holds counts only, with no personal data.

## Error handling

Each bronze load checks the source data against its table's column types before it writes anything, and makes all its changes in one step. If any value does not fit, the source has two rows with the same key, a write is rejected, or the row-count check fails, the load:

- stops and reports the error to whatever ran it;
- records the run as 'Failed' in Layercake.etl_run_log, with the error message;
- leaves its table exactly as it was before the run.

For the corporate subscription load, the key is the contact number, scheme number and Campaign Year together. A source row where any of the three is missing fails the whole load in the same way; no row is skipped. So does a second source row with the same three values as another (see Known limitations).

For the concession bronze load, the key is the concession type id. A source row with no concession type id, or two rows with the same id, fails the whole load in the same way; no row is skipped (see Known limitations).

The member status load changed by MOD-017 keeps its Phase 1 error handling, which testing confirmed. It makes all its changes in one step. If a write is rejected part-way, or the row-count check fails, it undoes everything the run had done, records the run as 'Failed' with the error message and reports the error; brnz_subs_status is left exactly as it was. Because it runs inside the Phase 1 run, a failure there also stops the Phase 1 run at that point: the steps after it in that run do not run, and the Phase 1 run itself is recorded as failed. Unlike the new bronze loads, it does not fail on a source row with no contact number or Campaign Year, or on two source rows for the same contact and Campaign Year: as in Phase 1, the first are not landed and, of the second, the row with the latest Renewal Date Adj is kept.

The member base load changed by MOD-018 also keeps its Phase 1 error handling, which testing confirmed: if a write is rejected, it reports the error, records the run as 'Failed' with the error message and leaves silv_member_base exactly as it was after its last successful run. It too runs inside the Phase 1 run, so a failure there stops the Phase 1 run at that point, and the Phase 1 run is recorded as failed. The events load's error handling is unchanged.

The dimension loads and the list loads (line-type mapping, currency list and concession type list) also make all their changes in one step. If any write is rejected, the load reports the error, records the run as 'Failed' with the error message, and undoes everything the run had done, including any name, code or flag it had already corrected. A failed line-type mapping or currency list load adds no row at all, not even part of a run. The concession type list load also fails in this way, rather than storing a cut-down code, if a type's item code is longer than the list holds (see Known limitations).

The attributes load makes its additions, updates and deletions in one step too. If any of them fails part-way, it undoes them all, records the run as 'Failed' with the error message, and reports the error. It also fails in this way, before changing anything, when no Campaign Year in Layercake.ref_campaign_year_config covers its as-of date; the error message names the date.

The segment anomaly load works the same way. If any addition, rewrite or removal is rejected, or a case's key is too long for the table (see Known limitations), it undoes them all, records the run as 'Failed' with the error message, and reports the error. silv_data_anomaly is left exactly as it was, with every case from the last successful run still in place and rows of the other anomaly types untouched.

The invoice anomaly load works the same way too, and testing confirmed it. If any addition, rewrite or removal is rejected, or an event's identifier makes a case's key too long for the table (see Known limitations), it undoes them all, records the run as 'Failed' with the error message, and reports the error. silv_data_anomaly is left exactly as it was: a case the run would have removed is still there, a case it would have added is not, and rows of the other anomaly types are untouched.

The event amount load fails in the same way when an Inv Total Amount in brnz_subs_status is too large for the event amount columns (see Known limitations): it reports the error, records the run as 'Failed' with the error message, and leaves silv_event_amount exactly as it was, with every row from the last successful run in place.

The silver event column load makes all its updates in one step. If any is rejected, it undoes them all, records the run as 'Failed' with the error message and reports the error; silv_membership_events is left exactly as it was, including events the run had already updated. The gold event column load works the same way, and it also fails when its check finds that silver and gold disagree: the numbers of events by payment method or by amount status, or the amount totals, differ, for example because one table holds an event the other lacks. It then reports the error, records the run as 'Failed' with the error message, and leaves fact_membership_events exactly as it was. Testing confirmed both.

In plain terms, a failed load changes nothing, so it can simply be run again once the cause is dealt with.

The profiles only read their sources and write nothing, so a failed or interrupted profile run leaves the database exactly as it was.

## Recovery and reruns

After a failed load:

1. Read the error message on the 'Failed' row in Layercake.etl_run_log.
2. Deal with the cause. Where it lies in the source data (for example a duplicate row key, an amount too large for the table, a corporate subscription row with a missing contact number, scheme number or Campaign Year, a concession type with a missing or repeated id, or an Inv Total Amount in Subs.vwSubsMemberStatuses too large for the event amount columns, see Known limitations), the fix goes to the source's owner, because the solution does not change source objects. Where the attributes load failed because no Campaign Year covers its as-of date, Layercake.ref_campaign_year_config needs a row whose start and end dates cover that date.
3. Run the load again. Because the failed run changed nothing, no clean-up is needed first. Then run any load that reads its output (see Components and load order): after a failed attributes load, that includes the segment anomaly load and the two event column loads; after a failed event amount load, the invoice anomaly load and the two event column loads; and after a failed silver event column load, the gold one.

If the member status load (Layercake.usp_load_brnz_subs_status) fails inside the Phase 1 run, the steps after it in that run did not run, so once the cause is dealt with, run the Phase 1 run (Layercake.usp_run_daily_load) again rather than the load alone. The load can also be run on its own, for example to reload its table after a source fix.

The same applies if the member base load (Layercake.usp_load_silv_member_base) fails inside the Phase 1 run: once the cause is dealt with, run the Phase 1 run again. As in Phase 1, rerunning it picks up whatever the failed run did not finish, and no clean-up is needed.

Until the cause is dealt with, the table keeps the data from its last successful run.

A profile that fails or is interrupted can simply be run again.
