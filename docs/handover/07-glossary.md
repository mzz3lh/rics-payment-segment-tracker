# Glossary: RICS Payment Segment Tracker

## Terms

| Term | Meaning |
|---|---|
| Amount Campaign Year | The Campaign Year a Join, Renewal or Readmission takes its amount and its paired invoice from: its own Campaign Year for a Renewal or Readmission; for a Join, the Campaign Year of the contact's first paid position, or the Join's own year where the contact has none (RULE-032, assumed, Q-029). The invoice anomalies are raised only where it is 2022 or later. |
| Amount status (amount_status) | On each Join, Renewal and Readmission, the explanation of its amount, the first that applies: Before invoice data, No invoice, Counted on another event, Full Concession, Fully credited or Invoiced (RULE-088, Q-045). Change and Lapse events have none. |
| Annual rate base | The Phase 1 tables Layercake.silv_annual_rate_base and Layercake.fact_annual_rate_base: for each Campaign Year, counts of members at the start and end of the year and of joins, readmissions, lapses and renewals, by grade, membership status, country and gender. Worked out again in full on every Phase 1 run. |
| Anomaly | A case where the data does not match the agreed rules, recorded as one row of Layercake.silv_data_anomaly with its anomaly type, the contact and a description (detail). Phase 1 records eleven anomaly types; this solution adds the four segment anomaly types (MOD-008) and the six invoice anomaly types (MOD-011). Each anomaly type is looked after by one load only. |
| apuk_retirementdate (hand-entered retirement date) | The retirement date typed into the CRM membership record, landed in Layercake.brnz_rics_record. Phase 1 used it for Practising / Retired; since MOD-018 the derived retirement date replaces it, because it is not always trustworthy. |
| As-of date | The date the member-year attributes load treats as today, which sets the current Campaign Year. By default it is the day the load runs. |
| Audit columns | The four columns every bronze table carries: _loaded_at (first landed), _updated_at (last changed by a load), _is_deleted (1 when no longer in the source) and _deleted_at (when it was marked as deleted). |
| Bronze | The layer of tables that copy source data one-to-one, with no change to any value, plus the audit columns. Their names start brnz_. |
| Campaign Year | The RICS subscription year, as held in Layercake.ref_campaign_year_config and on the invoice source. |
| Carried forward | A segment value copied from the latest earlier Campaign Year with an eligible invoice, because the year itself has none. Marked by a carried flag of 1 (payment_method_carried, payer_type_carried, concession_type_carried). Concessions are carried only when perpetual (assumed, Q-006). |
| CONCESSION_NOT_IN_REFERENCE | The segment anomaly raised for each concession item code on a contact-year's segment invoice that is not in the concession type list (RULE-052). |
| Concession reference | The source list of concession types. Assumed to be CE.vwConcessionType, awaiting Q-008; landed in Layercake.brnz_concession. |
| Concession type | A reduced or nil subscription rate a member can hold, such as Retired or Exceptional Hardship, as listed in the concession reference. |
| Concession type list | Layercake.silv_ref_concession_type: the three reserved values, one 'No concession' row and one row per source concession type, each with an id that never changes, its invoice item code and its full-concession and perpetual flags. Copied to the concession type dimension, Layercake.dim_concession_type. |
| corporate_account_ref | On the member-year attributes, the scheme number of the contact's live corporate subscription in a Corporate year; empty in every other year (assumed, Q-019). |
| CORPORATE_FLAG_NO_SCHEME | The segment anomaly raised for a contact-year from 2022 whose segment invoice has payment method Corporate but where the contact is in no live corporate subscription that year (RULE-025, assumed, Q-002). |
| Corporate subscription | A contact's place in a corporate scheme subscription for a Campaign Year, as held in Subs.vwCorpSubscriptions and landed in Layercake.brnz_corporate_subscription. |
| Corporate status profile | Layercake.usp_profile_corp_subscription_status: counts rows of Subs.vwCorpSubscriptions by each 'Sub Status' and 'Sub User Status' value (Q-027). |
| Count-only query | A read-only query that returns counts, sums or rates only, never individual records, so it can be run on real data safely. |
| Counted on another event | The amount status of a Join, Renewal or Readmission whose contact and amount Campaign Year has its amount on another event: a Readmission first, then a Renewal, then a Join, then the earliest date, then the lowest event_id (RULE-098, Q-039, Q-047). Its amounts are empty, so no contact-year's amount is counted twice. |
| Credit note | A document on the invoice source whose number contains 'FTCN', or contains 'CRE' unless its full amount is exactly 0 (RULE-014). A credit note is never an eligible invoice. |
| Currency list | Layercake.silv_ref_currency: one row per currency code found on the subscription invoices, each with an id that never changes. Copied to the currency dimension, Layercake.dim_currency. Under the amended specification it describes no event amount. |
| Current Campaign Year | The Campaign Year in Layercake.ref_campaign_year_config whose start and end dates cover the as-of date. The member-year attributes run up to and including it. |
| Daily counts | The Phase 1 day-by-day member counts in Layercake.silv_daily_count_detail and the gold Layercake.fact_daily_member_count_detail, from 1 October 2020. The daily run loads only days not yet loaded; days already loaded change only when a rebuild is run. |
| Derived retirement date | A member's retirement date taken from the member invoice statuses: the Renewal Date of their earliest live Campaign Year whose Retired Concession is 'Retired Conc.' and which has a Renewal Date (RULE-099). Given by Layercake.vw_silv_derived_retirement_date and held in silv_member_base.retirement_date. A member with no such year has none, with no fallback (Q-040). |
| Dimension | A gold table that reporting uses to show a segment by name, such as Layercake.dim_payment_method, Layercake.dim_payer_type, Layercake.dim_currency or Layercake.dim_concession_type. Their names start dim_. |
| Double payment | A segment invoice settled both by Corporate and by another payment method. The contact-year is Corporate where a live corporate subscription exists, otherwise Individual, and one DOUBLE_PAYMENT anomaly is recorded either way (RULE-026, assumed, Q-002). |
| Eligible invoice | A subscription invoice that may set a contact-year's segments (RULE-014): not a credit note, not fully credited and not fee-only. A fully credited invoice is eligible only when the contact-year has no other eligible invoice (assumed, Q-012). Listed by Layercake.vw_silv_eligible_invoice, which the event amount load also uses to pair events with invoices, and the invoice anomaly load to find invoices no event is paired with. |
| Event amounts | Layercake.silv_event_amount (MOD-010): one row per Join, Renewal and Readmission, with its amount Campaign Year, invoiced amount, amount status, paired invoice and match outcome. The design keeps it internal to silver; the amounts reach reporting through the event tables (MOD-012), and the invoice anomalies are worked out from its pairing (MOD-011). |
| Event identifier (event_nk, event_id) | The two identifiers of a membership event in the Phase 1 event tables: event_nk, an identifier text such as 'RN:A1:2025', and event_id, a number. Events on the same date are paired with invoices in event_nk order; the amount tie goes to the lowest event_id. An invoice anomaly about an event names it by its event_nk. |
| EVENT_MATCHES_MULTIPLE_INVOICES | The invoice anomaly raised for each surplus invoice: an eligible invoice left unpaired because its contact and amount Campaign Year has more eligible invoices than Join, Renewal and Readmission events. The earlier invoices are the surplus. Such an invoice gets no INVOICE_NO_EVENT row (RULE-091). |
| EVENT_NO_INVOICE | The invoice anomaly raised for each Join, Renewal or Readmission from 2022 whose contact and amount Campaign Year has no eligible invoice (RULE-042). |
| Event tables | The Phase 1 tables Layercake.silv_membership_events (silver) and Layercake.fact_membership_events (gold), one row per membership event (Join, Change, Lapse, Readmission, Renewal). |
| Fee-only invoice | An invoice whose own lines include at least one enrolment or application fee line and are otherwise only tax. It is not an eligible invoice. |
| Free-readmission window | The second quarter of a Readmission's Campaign Year, months four to six counted from the Campaign Year's start date: 1 January to 31 March for a Campaign Year starting 1 October, the same quarter as Phase 1's campaign quarter Q2 (RULE-092, Q-032). A Readmission in it whose invoice has no readmission fee line is READMISSION_FREE. |
| Full concession | A concession type whose discount in the concession reference is exactly 100, also called a full-rate concession; any other discount is a reduced concession (RULE-047). Marked by is_full_concession. |
| Full Concession position | A contact-year whose paid invoice position is Full Concession, one of the Phase 1 paid positions. |
| FULL_CONCESSION_NO_CONCESSION | The segment anomaly raised for a Full Concession position whose segment invoice carries no full-rate concession (RULE-053). |
| Fully credited | An invoice whose fully-credited value is 'Y'; 'N', 'N/A' and a missing value are not fully credited. |
| Gold | The layer that reporting reads: the dimensions and the fact tables. |
| Grain | What one row of a table represents, for example one invoice line or one whole transaction. |
| Grain profile | Layercake.usp_profile_custtrans_grain: counts invoices in synapse_fo.CUSTTRANS_RICS by rows, different item codes and tax rows, to show the source's grain (Q-021). |
| Inv Total Amount (inv_total_amount) | In the member invoice statuses, a contact-year's invoiced total in GBP over its invoices that are not fully credited, as the owner's source works it out. Landed in Layercake.brnz_subs_status as inv_total_amount (MOD-017); under the amended specification it is the only source of an event's invoiced amount, taken by the event amount load (MOD-010; REQ-008, Q-038). |
| Invoice anomalies | The six anomaly types recorded by Layercake.usp_load_silv_data_anomaly_invoice (MOD-011) for amount Campaign Years from 2022, from the pairing of events with invoices: EVENT_NO_INVOICE, INVOICE_NO_EVENT, INVOICE_MATCHES_MULTIPLE_EVENTS, EVENT_MATCHES_MULTIPLE_INVOICES, READMISSION_FREE and READMISSION_NO_FEE (REQ-009). |
| INVOICE_MATCHES_MULTIPLE_EVENTS | The invoice anomaly raised for each event left without an invoice because its contact and amount Campaign Year has more events than eligible invoices (an 'Invoice shortfall'). Such an event gets no EVENT_NO_INVOICE row (RULE-090). |
| INVOICE_NO_EVENT | The invoice anomaly raised for each eligible invoice from 2022 in a contact-year where no Join, Renewal or Readmission takes its amount from that year (RULE-043). |
| Invoice pairing (match outcome) | The pairing of each Join, Renewal and Readmission from 2022 with its own eligible invoice for its contact and amount Campaign Year, in date order, used only for the invoice checks (MOD-011) and never for an amount (RULE-084 to RULE-086). Its outcome is Matched, No eligible invoice, Invoice shortfall or Before invoice data. |
| Invoice shortfall | The match outcome of an event left without an invoice because its contact and amount Campaign Year has more events than eligible invoices; the invoices go first to a Readmission, then a Renewal, then a Join, then the earliest date (RULE-085). Recorded as the anomaly INVOICE_MATCHES_MULTIPLE_EVENTS. |
| Invoiced subtotal (invoiced_subtotal_gbp) | An event's headline amount: its contact-year's Inv Total Amount in GBP, on the one event that carries it (RULE-087, RULE-033). |
| Item code (productcode) | The code on an invoice row that says what the row is for, for example a subscription, a fee or a concession. The line-type mapping turns it into a line type, and each concession type carries the item code its invoice lines use. |
| Last settlement voucher | On a credit or payment row in synapse_fo.CUSTTRANS_RICS, the voucher of the invoice it settles (RULE-077). |
| Layercake | The database schema that holds the Phase 1 membership solution and every object this solution adds. |
| Line type | What an invoice line is for: subscription, concession, readmission fee, enrolment or application fee, tax, other, or unmapped (RULE-028). |
| Line-type mapping | Layercake.silv_ref_invoice_line_type: the table that gives the line type of each item code and RIC invoice type pair. New codes are added as 'unmapped'; a person sets their line type by hand, and the load never overwrites it. |
| Live corporate subscription | A row in Subs.vwCorpSubscriptions for the contact and Campaign Year where both 'Sub Status' and 'Sub User Status' are active. Which value means active is an assumption ('Active') awaiting Q-027. |
| Live row | A bronze row whose source row still exists (_is_deleted 0). |
| Load log | Layercake.etl_run_log: one row per load run, with its outcome ('Success' or 'Failed') and the rows inserted, updated and deleted. |
| load_id | On a dimension, reference list, member-year attributes or event amounts row, the load log entry of the load run that last wrote the row. |
| Marked as deleted (soft delete) | A bronze row whose source row has gone is kept, with _is_deleted set to 1 and _deleted_at recorded, rather than removed. |
| Member base | Layercake.silv_member_base: the Phase 1 table with one row per member that every later Phase 1 derivation reads, worked out again in full on every Phase 1 run. Since MOD-018 its retirement_date holds the derived retirement date. |
| Member invoice statuses | Subs.vwSubsMemberStatuses, the owner's view of each contact's invoice position for each Campaign Year (one row per contact and Campaign Year), landed by Phase 1 in Layercake.brnz_subs_status. It holds the Member Invoice Position, the Renewal Date and, since MOD-017, Inv Total Amount and Retired Concession. |
| Member profile | Layercake.silv_member_profile: a Phase 1 table kept in step with the member base, including a copy of the retirement date, which the daily counts read. When retirement dates change, its load records a pending daily rebuild. |
| Member-year attributes | Layercake.silv_member_year_attributes: one row per contact per Campaign Year, from the contact's first membership event to the current Campaign Year, holding the year's payment method, payer type, corporate_account_ref and concession, each segment with a carried flag. |
| Membership status (Practising / Retired) | The Phase 1 status on events, annual rates and daily counts (membership_status_id). A member is Retired from their retirement date, inclusive, which since MOD-018 is the derived retirement date; the rest of the Phase 1 status rule is unchanged (RULE-100). |
| Migration | A numbered, recorded change to the database (MIG-nnnn), with an up script that applies it and a down script that reverses it. |
| No concession | The row of the concession type list for a member whose invoice carries no concession. It is put in place by the migration, not read from the source. |
| Paid position | In Phase 1, a contact's paid invoice position for a Campaign Year (Full Concession, Fully Paid, Partially Paid or Pre-Subs Payment), held in Layercake.silv_payment_events. Needed for a contact-year to be Individual, and sets a Join's amount Campaign Year. |
| Payer type | The segment that marks each membership event and paid member as Individual or Corporate. Its list of values is Layercake.silv_ref_payer_type. |
| Payment line | A live row of the invoice lines, on the invoice's own account, whose last settlement voucher is the invoice's voucher and which carries a payment mode. Payment lines decide the payment method when the segment invoice has no payment mode (RULE-013). |
| Payment method | One of the five ways a member pays that the dashboard filters on: Direct Debit, Card, Bank transfer, Cheque and Corporate. There is no Mixed method, an assumption awaiting Q-015. |
| Payment mode code | The code the finance system records for how an invoice or payment is paid: DD, Card, Bank, Cheque or Corporate. Layercake.fn_map_payment_method turns it into a payment method. |
| Payment source (payment_source) | A former text column on the Phase 1 table Layercake.silv_payment_events, which only ever held its default, 'Individual'. Removed by MOD-009 (RULE-027); the payer type on the member-year attributes takes its place. |
| Pending daily rebuild | A row in Layercake.etl_daily_count_pending_rebuild recording that a change reaches back into daily counts already loaded, with its source (for example 'member_profile') and the earliest affected day (affected_from). The daily run does not apply it; a run of Layercake.usp_load_silver with @RebuildFrom (or @FullRebuild = 1) does, and marks it as applied. |
| Perpetual concession | A concession type marked Perpetual (value 200000000) in the concession reference; every other value, including Non-Perpetual and a missing value, is not perpetual (RULE-094). Marked by is_perpetual. |
| Phase 1 | The existing Layercake membership solution that this solution extends. Under the amended specification, only its results split by membership status (Practising / Retired) change, since MOD-018; all its other counts and measures stay the same. |
| Phase 1 run | The existing daily Phase 1 load, Layercake.usp_run_daily_load, which runs the Phase 1 bronze, silver and gold steps in order. The member status load changed by MOD-017 runs in its bronze step, and the member base and events loads changed by MOD-018 in its silver step. |
| Readmission fee line | One of a paired invoice's own live lines (same account and voucher) whose line type in the line-type mapping is 'readmission fee'. The readmission checks look for one; they never read the event amount (RULE-044, Q-042). |
| READMISSION_FREE | The invoice anomaly raised for a Readmission from 2022 whose paired invoice has no readmission fee line, when the Readmission falls in the free-readmission window (RULE-044, RULE-092). |
| READMISSION_NO_FEE | The invoice anomaly raised for a Readmission from 2022 whose paired invoice has no readmission fee line, when the Readmission falls outside the free-readmission window (RULE-044). |
| Reference list | A silver table listing the values of a segment or code, with ids or keys that never change, for example Layercake.silv_ref_payment_method, Layercake.silv_ref_payer_type, Layercake.silv_ref_currency or Layercake.silv_ref_concession_type. Their names start silv_ref_. |
| Renewal Date | In the member invoice statuses, a contact-year's first payment date or, for a Full Concession invoice, the date the concession settled the invoice, kept inside the Campaign Year (Q-041). It gives the derived retirement date. |
| Reserved values | Three fixed entries in every segment list: 0 Unknown (the source has no value), -1 Unrecognised (the source has a value the mapping does not know) and -2 Not applicable (no value is expected). |
| Resolved (anomaly) | A Phase 1 anomaly that is no longer detected is kept and marked as resolved (resolved_at), and re-opened if it recurs. Segment and invoice anomalies are not marked as resolved: a case that no longer applies is removed. |
| Retired Concession (retired_concession) | In the member invoice statuses, one of 'No Invoice', 'No Conc.', 'Retired Conc.' or 'Non-Retired Conc.' for a contact-year. 'Retired Conc.' means at least one of the contact-year's invoices that is not fully credited carries one of the six retired concession item codes. Landed in Layercake.brnz_subs_status as retired_concession (MOD-017), and used for the derived retirement date (MOD-018, REQ-017). |
| RIC invoice type (ricinvoicetype) | The invoice type recorded on each row of synapse_fo.CUSTTRANS_RICS. With the item code, it identifies a row of the line-type mapping; a missing type is treated as empty. |
| Round | A column in Subs.vwCorpSubscriptions marking a tranche of processing of corporate records; later rounds may change it. It is not landed and plays no part in the solution. |
| Scheme No (scheme number) | The number of a corporate scheme subscription in Subs.vwCorpSubscriptions. With the contact number and Sub Campaign Year, it identifies a corporate subscription row. |
| Segment anomalies | The four anomaly types recorded by Layercake.usp_load_silv_data_anomaly_segment for contact-years from 2022 with a segment invoice: CORPORATE_FLAG_NO_SCHEME, DOUBLE_PAYMENT, CONCESSION_NOT_IN_REFERENCE and FULL_CONCESSION_NO_CONCESSION. |
| Segment invoice | The eligible invoice that sets a contact-year's payment method, payer type and concession: the latest by transaction date (RULE-079, assumed, Q-012), ties to the higher row key (Q-036). |
| Sub Status, Sub User Status | In Subs.vwCorpSubscriptions, the status of the corporate subscription and the status of the subscription user. |
| Subscription amount (subs_amount_gbp) | On each Join, Renewal and Readmission, always the same value as the invoiced subtotal, and empty with it (RULE-035, Q-044). It is not a subscription-only figure separate from fees, because the member invoice statuses supply no fee amount. |
| Surplus invoice | An eligible invoice left unpaired because its contact and amount Campaign Year has more eligible invoices than events; the events take the latest invoices and the earlier ones are the surplus (RULE-086). Recorded as the anomaly EVENT_MATCHES_MULTIPLE_INVOICES. |
| REQ, RULE, AC, Q | Specification identifiers: a requirement, a business rule, an acceptance criterion and an open question to the client. |
| MOD, TC, ADR | A module of the build, a test condition, and an architecture decision record. |
| Silver | The layer of tables between bronze and gold: reference lists, attributes and matches. |
| Synthetic data | Made-up test data, used for all automated testing; no real data is used in testing. |
| Unmapped | The line type given to an item code that has not yet been mapped. It stays visible as 'unmapped' until a person maps it by hand. A line with no mapping row also counts as unmapped. Under the amended specification, unmapped lines no longer affect any event amount (RULE-030), but an unmapped fee code does not count as a readmission fee line. |
| Voucher | The reference that links an invoice in Subs.tblSubsInvoices to its rows in synapse_fo.CUSTTRANS_RICS: an invoice's own lines carry its voucher (RULE-077). |
