## RULE-077 settling rows (Mike, 2026-10-26)

## MOD-005 NULL, blank and near-duplicate codes (Mike, 2026-10-27)
- usp_load_silv_ref_invoice_line_type takes codes from live brnz_subs_invoice_line rows. A row whose productcode is NULL, empty or only spaces has no item code and adds no mapping row.
- A row with a productcode but a NULL ricinvoicetype is not skipped. Its code is added with ric_invoice_type N'' (empty string) and line type 'unmapped', so the invoice is flagged 'Unmapped lines' (RULE-088) rather than its amount being lost unseen, and the pair can be mapped by hand like any other. Any later load that joins lines to the mapping treats a NULL ricinvoicetype as N''.
- Codes are matched as the database collation compares them (case-insensitive, trailing spaces ignored). A productcode or ricinvoicetype that differs from a listed pair only in case or trailing spaces is that pair: no new row, and it takes that pair's line type. A code with different leading spaces or characters is a new code and is added as 'unmapped'.
- usp_load_silv_ref_currency works the same way: an inv_currency that is NULL, empty or only spaces adds no row, and a code that differs from a listed one only in case or trailing spaces adds no row.

## MOD-007 attributes load (approved by Mike by merging this PR, 2026-10-27)
- Contact list and first-event year (RULE-011, Q-030): the contacts are every contact_no in Layercake.silv_membership_events, and a contact's first-event year is MIN(campaign_year) over all their events there. silv_member_base is not used: it holds no event year and is deliberately not unique on contact_no. Each contact gets one row per Campaign Year in Layercake.ref_campaign_year_config, from the first-event year to the current Campaign Year inclusive. A contact whose first event is after the current Campaign Year gets no rows. contact_no is nvarchar(200), the Phase 1 type (DES-001 said nvarchar(20); this PR corrects it on silv_member_year_attributes and silv_event_amount).
- Current Campaign Year: the ref_campaign_year_config row whose campaign_year_start <= @as_of_date <= campaign_year_end. The load is `Layercake.usp_load_silv_member_year_attributes @run_id uniqueidentifier = NULL, @as_of_date date = NULL`, where NULL means CAST(SYSDATETIME() AS date), so the scheduled run needs no argument and tests pass a fixed date. If no config row covers @as_of_date, the load fails: it logs Failed, re-raises and changes nothing.
- Phase 1 paid position (RULE-021, RULE-017): a contact has a paid position in a Campaign Year when Layercake.silv_payment_events has a row for that (contact_no, campaign_year). That table holds only the paid invoice positions (Full Concession, Fully Paid, Partially Paid, Pre-Subs Payment), so no further filter on invoice_position is applied. brnz_subs_status is not read directly.
- Eligible invoice (RULE-014, vw_silv_eligible_invoice): only live invoices count (brnz_subs_invoice._is_deleted = 0) with a non-NULL account_num and campaign_year; contact_no = account_num.
  - (a) Credit note: invoice LIKE '%FTCN%', or invoice LIKE '%CRE%' unless full_invoice_amount_cur = 0. This matches the owner's test, which lets a CRE invoice through only when its amount is 0, so a CRE invoice with a NULL amount is a credit note. A NULL invoice number is not a credit note.
  - (b) Fully credited: fully_credited = 'Y'. Subs.usp_Refresh_SubsInvoices sets 'Y', 'N' or 'N/A'; anything other than 'Y', including NULL, is not fully credited.
  - (c) Fee-only: the invoice's own lines are the live brnz_subs_invoice_line rows with accountnum = account_num and voucher = voucher. Each is typed through silv_ref_invoice_line_type on productcode = item_code and ISNULL(ricinvoicetype, N'') = ric_invoice_type; a line with no mapping row counts as unmapped. The invoice is fee-only, and not eligible, when it has at least one 'enrolment or application fee' line and every other own line is 'tax'. An invoice with no own lines is not fee-only, so it stays eligible.
  - Fallback: where a contact-year has no invoice passing (a), (b) and (c), its fully credited invoices that pass (a) and (c) are eligible instead.
  - Segment invoice: the latest eligible invoice by trans_date, ties to the higher rec_id (Q-036); a NULL trans_date sorts before every date.
- Payment-line fallback (RULE-013): it applies only when the segment invoice's inv_payment_method is NULL or blank after trimming. A non-blank code the mapping doesn't know gives -1 Unrecognised, with no fallback.
  - Payment lines: the live brnz_subs_invoice_line rows with lastsettlevoucher = the invoice's voucher and accountnum = its account_num (RULE-077 answer), with a paymmode that is not NULL or blank. The invoice's own lines (voucher = the invoice's voucher) are not payment lines.
  - Choosing the method: each paymmode is mapped through fn_map_payment_method, and ABS(settleamountcur) is summed per mapped method, with a NULL amount counting as 0. The method with the largest sum wins. On a tie, the method whose earliest payment (MIN(transdate)) is earliest wins, and the lowest recid breaks any remaining tie. An unrecognised mode takes part like any other, so if it wins the year gets -1. With no qualifying payment line, the year gets 0 Unknown with flag 0 (RULE-015).
- Load pattern (DES-001): not a full rebuild. The load recomputes every contact-year, inserts new rows, updates rows whose values differ (refreshing updated_at and load_id, keeping created_at), deletes rows no longer derived and leaves unchanged rows untouched. A rerun on unchanged data therefore logs 0, 0, 0.
- Logging: the same as the MOD-004 to MOD-006 loads. Layercake.usp_etl_log_start @run_id, 'silver', 'silv_member_year_attributes' runs before the transaction, and usp_etl_log_end logs 'Success' with the inserted, updated and deleted counts. On error, CATCH rolls back, logs 'Failed' with the error message and re-raises (THROW).

## Invoice line grain (approved by Mike by merging this PR, 2026-11-11)
- Q-021, answered from real data on 2026-11-11 (counts only): synapse_fo.CUSTTRANS_RICS is not one row per transaction. RECID is the customer transaction's key (it equals CUSTTRANSRECID), and each transaction is split into one row per ledger distribution: one row per POSTINGTYPE and ACCOUNTDISPLAYVALUE, the ledger account string that carries main account, cost centre, country, item code (productcode) and, where set, Campaign Year (RICSCAMPAIGNYEAR). 458,563 RECIDs occur on more than one row (1,015,865 rows): 456,807 invoice transactions (TRANSTYPE 2) and 1,756 payment transactions (TRANSTYPE 8). For example, one back-subs payment is split into one line per Campaign Year.
- (RECID, POSTINGTYPE, ACCOUNTDISPLAYVALUE) is unique in CUSTTRANS_RICS; (RECID, POSTINGTYPE, MainAccount, productcode) is not, because one item code can be split across cost centres or Campaign Years. Layercake.usp_load_brnz_subs_invoice_line currently fails with a duplicate key on its recid-keyed staging table.
- Layercake.brnz_subs_invoice_line lands every CUSTTRANS_RICS row in scope (RULE-077 unchanged), keyed on (recid, postingtype, accountdisplayvalue), and also lands postingtype, accountdisplayvalue, mainaccount, costcenter and ricscampaignyear. The rows are not aggregated. ACCOUNTDISPLAYVALUE is nvarchar(500) in the source, longer than SQL Server's 900-byte clustered key limit, so how the key is enforced is the Architect's call.
- AMOUNTCUR and AMOUNTMST are the line's own amounts. The transaction-level columns (SETTLEAMOUNTCUR, and CustTrans_AmountCur and CustTrans_AmountMst if used) repeat on every line of a transaction, so every reader takes them once per RECID and never sums them across a transaction's lines. ## Daily load accuracy (approved by Mike by merging this PR, 2026-11-17)
- Mike, 2026-11-17: "I want the build to rebuild the numbers where necessary to keep it accurate. However, I also want to retain a history of adjustments in an easy format, so that numbers on a particular day can be easily calculated if required."
- What happens today (from the code, src/sql/Layercake/Procedures): Layercake.usp_load_silv_daily_count is forward only. A past date is derived once, marked in Layercake.etl_daily_count_loaded and never derived again unless someone runs usp_load_silver @RebuildFrom or @FullRebuild. Only today is rebuilt on every run. The silver it reads (silv_membership_events, silv_member_state_ranges, silv_payment_events, silv_member_profile) is re-derived on every run, so stored history drifts away from it. Producers log a pending rebuild in Layercake.etl_daily_count_pending_rebuild (state_ranges, payments, member_profile, enrol_exception), but nothing applies it, and silv_membership_events logs nothing at all. paid_count_event and the Join, Renewal and Readmission flows are worst hit, because a late or backdated event changes every day from its date to the end of its campaign year. Layercake.fact_daily_member_count_detail already diffs the whole silver span on every run, so gold follows silver once silver is right.
- Rebuild: every run of Layercake.usp_run_daily_load brings every past date whose counts no longer match the current silver data back into line, in the same run, with no manual step. This covers silv_daily_count_detail and silv_daily_count (and so fact_daily_member_count_detail), every measure (active_count, paid_count, paid_count_event and the four event flows), and every cause, including event-only changes that log no pending rebuild today. How changed dates are found is the Architect's call. The test is that after any run, the stored history is identical to what @FullRebuild = 1 would produce on the same data.
- Horizon: the whole spine from 2020-10-01. Closed campaign years are not frozen.
- Adjustment history: a new Layercake table keeps one row for each cell whose numbers changed, for each run that changed it, at the grain of silv_daily_count_detail ([date], region, country_id, gender_id, grade, membership_status_id). Each row holds the run_id, when it was written, the date and grain columns, and the change (new minus old) for each of the seven measures. A first load of a date that has never been loaded is not an adjustment and writes no row. Repeat loads of today (today is rebuilt on every run) are adjustments like any other.
- "As known at" any point in time: the figure for any date, as it stood at time T, is today's stored figure minus the changes written after T. A view or function in Layercake gives this at the silv_daily_count grain and at the detail grain, for a date range and a time T, so nobody has to write the subtraction by hand. A second view lists the adjustments by date, run and measure for review.
- Retention: the adjustment history is kept indefinitely; nothing purges it.
- Catch-up: the first run after this change is deployed does the catch-up for the drift so far. This replaces the ASM-002 one-off usp_load_silver @RebuildFrom. Its changes go into the adjustment history like any other run, so the size of the drift up to now can be read from it.
- @RebuildFrom and @FullRebuild stay as manual tools, and the changes they make are written to the adjustment history too. Whether etl_daily_count_pending_rebuild stays (as a diagnostic) or is retired is the Architect's call, but nothing may depend on a person applying it.
- Run time: a run will take longer on days when a change reaches far back. That is accepted. A run that fails part way must resume on the next run with no manual cleanup, as the daily count does today, and the adjustment history must never hold a change that was rolled back.
- Out of scope: the P01/P03 timing difference (our bronze load runs before Subs.usp_Refresh_SubsMemberStatuses; Mike accepts it for now), the annual rate base tables (they are re-derived in full on every run), and Power BI work.

## Corporate subscription repeated keys (approved by Mike by merging this PR, 2026-11-18)
- Mike, 2026-11-18: the first production run of Layercake.usp_run_daily_load after MIG-0023 to MIG-0025 failed in Layercake.usp_load_brnz_corporate_subscription with error 2627 on #src_corporate_subscription, a repeated (Contact No, Scheme No, Sub Campaign Year) key in Campaign Year 2027. Phase 1 and the two invoice bronze loads committed; the corporate subscription table was left unchanged and the later segment loads did not run.
- Q-033 is answered: No. Subs.vwCorpSubscriptions is at subscription-user grain (CE.vwRicsv2Subscription joined to CE.vwSubscriptionUser), and a contact can hold several subscription-user records on one subscription and Campaign Year, for example removed in one round and added again in a later one. Counts from production, 2026-11-18: repeated keys in every Campaign Year from 2022 to 2027 (2027: 563 keys, up to 4 rows per key). Within every repeated key the Contact ID, Sub Start Date, Sub End Date and Scheme Name are the same; only the subscription-user columns (Round, Sub User State, Sub User Status, Sub User Created Date) differ, and 14 keys repeat identical rows. No key has more than one copy with Sub Status and Sub User Status both 'Active'.
- Rule: usp_load_brnz_corporate_subscription lands one row per (Contact No, Scheme No, Sub Campaign Year). Where the source holds several rows for a key, it keeps, in this order: the copy whose Sub Status and Sub User Status are both the active value (Q-027, 'Active'); then the copy with the latest Sub User Created Date; then the highest Round. Any remaining tie (identical rows, or rows equal on those columns) is broken deterministically so that the same source data always lands the same row; the exact final tie-break is the Architect's call.
- Repeated rows are not an error and do not fail the load. The number of source rows not landed as repeats is logged on every run (how is the Architect's call, for example a Layercake.etl_progress_log sub-step). They are not a data anomaly.
- Unchanged: a NULL Contact No, Scheme No or Sub Campaign Year still fails the load (2026-10-26). 'Round' is still not landed and plays no part except as the tie-break above (2026-10-23). The row-count check (RULE-005) compares the number of distinct keys in the source with the active bronze rows.
- Readers (usp_load_silv_member_year_attributes, usp_load_silv_data_anomaly_segment and the three MOD-014 employer reports) are not changed: each only asks whether a live 'Active'/'Active' row exists for the contact and Campaign Year, which the rule preserves.
- The existing MOD-004 tests built on Q-033 (a repeated key fails the load with 2627, TC-004-018's precondition) are superseded and are changed to the new rule.
- Handover: docs/handover/06-known-limitations.md (the Q-033 entry and the "one incomplete or repeated corporate subscription row stops the whole load" limitation) and the runbook are updated.
- Recovery after deployment: run EXEC Layercake.usp_run_payment_segments; once (or let the next Layercake.usp_run_daily_load run). Every segment load applies only differences, so no manual cleanup is needed.
- Out of scope: landing every subscription-user record (the view has no subscription-user key) and any change to Subs.vwCorpSubscriptions or the CRM data.

## Corporate subscription repeated keys: spec sign-off (approved by Mike by merging this PR, 2026-11-18)
- Q-053 (RULE-128 tie-breaks when no copy of a repeated key is 'Active'/'Active'):
  - A copy with a NULL 'Sub User Created Date' loses to every copy that has a date.
  - 'Round' holds text such as 'Round 1' and 'Round 2' in production, so it is not compared as text and not cast whole. It is compared by the whole number at its end (the digits after the last space, so 'Round 10' beats 'Round 9'). A NULL Round, or one that does not end in a whole number, counts as lowest.
  - Any tie left after that is broken deterministically, as the "Corporate subscription repeated keys" answers say, so the same source data always lands the same row.

## Corporate subscription repeated keys: architecture validation (approved by Mike by merging this PR, 2026-11-18)
- Q-054: yes, the Architect's reading of how RULE-128 compares Round is right. Leading and trailing spaces are ignored. The part after the last remaining space counts only if it is all digits; a value with no space is used whole. The number is compared by its value, so 'Round 10' and '10' both count as 10. 'Round 1a', 'Round', an empty value and NULL all count as lowest and tie with each other, and that tie goes to the deterministic final tie-break.
