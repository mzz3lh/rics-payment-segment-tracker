# Solution overview: RICS Payment Segment Tracker

## Purpose

The RICS Payment Segment Tracker adds financial segments and invoiced amounts to the existing Phase 1 membership solution (the Layercake schema). When complete, every membership event (Join, Change, Lapse, Readmission, Renewal) and every paid member can be filtered by payment method, payer type (Individual or Corporate) and concession type. Each Join, Renewal and Readmission will carry the amount invoiced for it, with one headline value in GBP. Phase 1 counts and measures do not change.

## Scope

The release covers the payment method, payer type and concession segments, invoiced amounts on events, and count-only queries for profiling and coverage. The employer segment is delivered as findings only in this release. Steps that need real data (profiling, reconciliation to Finance figures, team reviews and traces of real contacts) are done by a person, using the count-only queries the solution provides. Updating the Platform Schema document is also outside the solution: this pack supplies its content and a person updates it.

The solution is delivered in modules (MOD-nnn), each built and tested in turn. This pack currently covers:

- MOD-001, Source profiling queries: two read-only procedures that profile the source data before the invoice build.
- MOD-002, Subscription invoice bronze: two tables that land the subscription invoices and their invoice lines from the warehouse unchanged, and the loads that keep them up to date. This module does not interpret line types or payment modes; later modules do.
- MOD-003, Payment method reference and dimension: the fixed list of payment methods, the rule that turns a source payment mode code into one of them, and the payment method dimension for reporting. This module does not yet work out any contact's payment method; a later module (MOD-007) does.
- MOD-004, Corporate subscription bronze and payer type reference: a table that lands the corporate scheme subscriptions unchanged and the load that keeps it up to date, the fixed list of payer types (Individual and Corporate), and the payer type dimension for reporting. This module does not yet work out any contact's payer type; a later module (MOD-007) does.
- MOD-005, Invoice line-type mapping and currency: the mapping that says what each invoice item code is for (subscription, concession, readmission fee and so on), to which new item codes are added automatically as 'unmapped'; the list of invoice currencies; and the currency dimension for reporting. This module does not yet compute any amounts; a later module (MOD-010) does.
- MOD-006, Concession reference and dimension: a table that lands the concession types from the CRM concession reference unchanged and the load that keeps it up to date; the concession type list, which takes in new types and changed names while every type keeps its id, and records for each type its invoice item code and whether it is a full concession and whether it is perpetual; and the concession type dimension for reporting. This module does not yet work out any contact's concession; a later module (MOD-007) does.

Later modules are added to the pack as they pass testing.

## Requirements delivered

Requirements are numbered REQ-nnn and each has acceptance criteria (AC-nnn-nn) that the tests check. Business rules are numbered RULE-nnn and open questions to the client Q-nnn.

| Requirement | What it delivers | Status |
|---|---|---|
| REQ-002 Bronze landing of subscription invoices and invoice lines | The invoice-level data (payment method, currency, amounts, credits, payment status, concession flags) from Subs.tblSubsInvoices, landed in Layercake.brnz_subs_invoice, and the line-level data (item codes, line amounts, payment and credit lines) from synapse_fo.CUSTTRANS_RICS, landed in Layercake.brnz_subs_invoice_line. | Delivered. All six acceptance criteria (AC-002-01 to AC-002-06) passed testing. The line data rests on an assumption about the source's grain awaiting Q-021 (see Known limitations). |
| REQ-003 Payment method reference list and dimension | Layercake.silv_ref_payment_method, the list of the five payment methods the dashboard filters on (Direct Debit, Card, Bank transfer, Cheque, Corporate) plus the three reserved values shared by every segment (Unknown, Unrecognised, Not applicable); the mapping from source payment mode codes to that list; and the gold dimension Layercake.dim_payment_method, copied from the list. | Delivered. All six acceptance criteria passed testing: AC-003-01 to AC-003-05 in MOD-003, and AC-003-06, that the reserved values carry the same ids and labels in the payment method, payer type and concession type lists, in MOD-006. The list has no Mixed value, an assumption awaiting Q-015 (see Known limitations). |
| REQ-006 Payer type (Individual or Corporate) | So far: the corporate scheme subscriptions from Subs.vwCorpSubscriptions, landed in Layercake.brnz_corporate_subscription; the payer type list, Layercake.silv_ref_payer_type (the three reserved values plus Individual and Corporate); and the gold dimension Layercake.dim_payer_type, copied from the list. When complete, every membership event and paid member is marked Individual or Corporate. | Partly delivered. AC-006-01, the payer type list and its dimension, passed testing. Working out each contact's payer type for each Campaign Year, and the rest of REQ-006, come in later modules (from MOD-007). |
| REQ-007 Invoice line-type mapping and currency reference | Layercake.silv_ref_invoice_line_type, the mapping from invoice item code to line type, held in a table so new item codes show up as 'unmapped' rather than being dropped, and kept when mapped by hand; Layercake.silv_ref_currency, one row per currency found on the subscription invoices, with ids that never change; and the gold dimension Layercake.dim_currency, copied from it. | Delivered. All three acceptance criteria (AC-007-01 to AC-007-03) passed testing. The mapping starts with 12 item codes only, so most item codes will need mapping by hand after the first load on real data (see Known limitations). |
| REQ-010 Concession type reference and dimension | Layercake.brnz_concession, a one-to-one copy of the concession reference, CE.vwConcessionType; Layercake.silv_ref_concession_type, the concession type list built from it, holding the three reserved values, one 'No concession' row and one row per source concession type, each with its invoice item code, a full-concession flag and a perpetual flag; and the gold dimension Layercake.dim_concession_type, copied from the list. | Delivered. All six acceptance criteria (AC-010-01 to AC-010-06) passed testing. That CE.vwConcessionType is the concession reference is an assumption awaiting Q-008 (see Known limitations). |
| REQ-014 Count-only profiling and coverage queries | Queries that return counts only, run on real data by Mike, with the results brought back as answers to open questions. Delivered so far: the CUSTTRANS_RICS grain profile (AC-014-07) and the corporate subscription status profile (AC-014-08). | Partly delivered. The two source profiles passed testing. The coverage queries (AC-014-01 to AC-014-06) come in a later module (MOD-015). |

For what each object does, see the Architecture and data model document. For the test results, see the Test summary.
