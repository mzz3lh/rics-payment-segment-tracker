# ADR-011: How the daily count knows a changed contact's old contribution and recognises an emptied cell

| | |
|---|---|
| Status | proposed |

| Requirement IDs | REQ-024, REQ-018, REQ-019 |

## Context
Mike asked for a faster daily load (AMD-006). Production runs of Layercake.usp_load_silv_daily_count take 32 to 50 minutes. That is because the ADR-007 correction recomputes every date from the earliest affected date, and for any long-standing member that date is 2020-10-01. Only 67 to 394 of 178,751 contacts change on a normal day. REQ-024 (RULE-141) asks a normal run to recompute only the contacts whose inputs changed, for the dates their old and new inputs reach. RULE-144 lets the design rely on the count rule being additive per contact: on any day a contact sits in at most one detail cell, so each measure in a cell is the sum of its contacts' contributions. The results must not change (RULE-143): the tables and the adjustment history must equal what the full recompute gives. That means taking a changed contact's old contribution out of its cells and adding its new one. The spec leaves two things to the design: how the old contribution is known, and how a cell that loses its last contact is recognised and removed. Two more constraints follow. A run that fails part way must resume with no cleanup and must never record a rolled-back change (RULE-149). The MOD-021 and MOD-022 tests must keep passing (RULE-154, AC-024-13). Those tests include TC-022-009, where a failed run keeps the date batches it committed and leaves etl_daily_count_input_basis unchanged. The adjustment table admits one row per run and cell. The silv_daily_count_detail column list cannot change (AC-001-05). The four silver inputs are re-derived on every run, so the old values are not available from them.

## Options
### Option A: Snapshot of each contact's inputs as last applied, with a per-cell contact count
Four new control tables hold each contact's daily count input rows as last applied: one header row per contact with its silv_member_profile columns, and its silv_member_state_ranges, silv_payment_events and silv_membership_events rows. They hold exactly the rows and columns the etl_daily_count_input_basis fingerprint covers. The existing basis still finds the changed contacts. For each changed contact, the unchanged derivation is applied twice, over the loaded dates: once to the snapshot (old contribution) and once to the current inputs (new contribution). The difference is applied to the cells. A fifth table, etl_daily_count_cell_contacts, holds the number of contacts sitting in each loaded detail cell. That number is an eighth additive figure, kept like the seven measures, and a cell is removed when its count falls to 0. The snapshot and the basis advance together in the run's final transaction. A run withdraws the snapshot rows of the contacts it applies in its first batch. So if a run does not finish, the snapshot and the basis disagree, and the next run takes the existing full-recompute path from 2020-10-01. That path is idempotent and resumes with no cleanup, as today.

Trade-offs: The old and new contributions come from one derivation applied to two sets of inputs, so parity with the full recompute is natural, and the derivation is not rewritten. The snapshot does not depend on dates, so the daily extension of the spine needs no extra writes. Storage is about the size of the four inputs' read columns plus about one count row per stored detail cell (about 1.8 million in production). It is five new tables. The basis and snapshot must be kept strictly in step: a contact with one but not the other forces the full path. Recovery after a failed run is a full recompute, which is slower (about as long as @FullRebuild) but rare, and it is the behaviour today. A normal run changes stored figures by adding deltas, so it relies on the overlapping range guard (RULE-145) and on the cell existence rule being confirmed from the Phase 1 code (Q-059).

### Option B: Stored per-contact contributions by date range at cell grain
One new table holds every contact's contribution to the daily counts as date ranges: contact, detail cell, first and last date, and the seven 0-or-1 contributions. A contact on an unchanged state for a run of days is one row. A changed contact's old contribution is read straight from the table for the dates being recomputed. It is replaced by its new contribution, split at batch boundaries, in the same batch transaction as the cell changes. A cell is empty when no contribution row covers it on that date, so no count table is needed. Because the table records what was applied date by date, a run that fails part way can resume on the changed-contacts path: on dates already committed, the old and new contributions are equal.

Trade-offs: Resume after a failure stays fast, and both the old contribution and emptiness are read directly, with no second pass of the derivation. But the Phase 1 derivation has to be re-expressed as contribution ranges, which is a larger rework of the procedure MOD-022 has just built and carries more risk to parity. Ranges must be split at Campaign Year and status boundaries. They cannot be left open-ended, because the spine and Campaign Year rows after the latest loaded date may still change without being a change (RULE-147). So every first load of a new date extends or adds a row for about 150,000 contacts. The table holds several million rows and has to be rebuilt in full by every full recompute.

## Recommendation
Option A: Snapshot of each contact's inputs as last applied, with a per-cell contact count. The snapshot keeps the unchanged Phase 1 derivation as the single source of every figure, old and new, so RULE-143's parity follows from the design rather than from a re-implementation. It needs no daily writes for unchanged contacts. It also leaves the MOD-022 full-recompute path, with its tested batching and resume behaviour (TC-022-009, TC-022-018), as the fallback for anything unusual. The one cost is that recovery after a failed run is a full recompute. Mike asked for failure and resume to work "as today", and today a failed run is completed by a full recompute, so that cost is accepted. The stored contribution ranges would make that rare case faster, at the price of re-expressing the derivation and rewriting about 150,000 ranges every day.

## Consequences
MOD-026 adds etl_daily_count_applied_contact, etl_daily_count_applied_state_range, etl_daily_count_applied_payment, etl_daily_count_applied_event and etl_daily_count_cell_contacts. It changes usp_load_silv_daily_count in three ways: the faster count form and the overlapping range guard on every path, and the changed-contacts path on a normal run. etl_daily_count_input_basis keeps its structure. It is now advanced in the run's final transaction together with the snapshot. The full-recompute path is taken for @FullRebuild, @RebuildFrom, a changed reference input (RULE-147), and a snapshot not in step with the basis. That last case covers the first run after deployment and the run after one that failed. The first run after deployment therefore takes about as long as @FullRebuild, and it writes no adjustment rows if the stored figures are already right (RULE-148). Every run logs the contacts recomputed and whether it took the full path (RULE-153). The cell existence rule depends on Q-059: if Phase 1 also drops cells whose seven measures are all 0, only the existence test in the procedure changes. If stored contribution ranges are chosen instead, MOD-026 builds one contribution table and no snapshot or count tables, the derivation is re-expressed in range form, resume stays on the normal path, and the first load of each new date extends every present contact's range. The gold cell sync (MOD-027) is the same under either option.
