# Solution overview: RICS Payment Segment Tracker

## Purpose

The RICS Payment Segment Tracker adds financial segments and invoiced amounts to the existing Phase 1 membership solution (the Layercake schema). When complete, every membership event (Join, Change, Lapse, Readmission, Renewal) and every paid member can be filtered by payment method, payer type (Individual or Corporate) and concession type. Each Join, Renewal and Readmission will carry the amount invoiced for its contact and Campaign Year, one headline value in GBP taken from the member invoice statuses (Subs.vwSubsMemberStatuses, 'Inv Total Amount'); the invoices set the segments and feed the anomaly checks, but never the amount. Under the amended specification, a retirement date derived from the first invoice with a retired concession replaces the hand-entered retirement date in the Practising / Retired logic, and this is now in place (MOD-018), so Phase 1 results split by membership status change. All other Phase 1 counts and measures stay the same.

## Scope

The release covers the payment method, payer type and concession segments, invoiced amounts on events, the derived retirement date, and count-only queries for profiling and coverage. The employer segment is delivered as findings only in this release. Steps that need real data (profiling, reconciliation to Finance figures, team reviews and traces of real contacts) are done by a person, using the count-only queries the solution provides. Updating the Platform Schema document is also outside the solution: this pack supplies its content and a person updates it.

The solution is delivered in modules (MOD-nnn), each built and tested in turn. This pack currently covers:

- MOD-001, Source profiling queries: two read-only procedures that profile the source data before the invoice build.
- MOD-002, Subscription invoice bronze: two tables that land the subscription invoices and their invoice lines from the warehouse unchanged, and the loads that keep them up to date. This module does not interpret line types or payment modes; later modules do.
- MOD-003, Payment method reference and dimension: the fixed list of payment methods, the rule that turns a source payment mode code into one of them, and the payment method dimension for reporting.
- MOD-004, Corporate subscription bronze and payer type reference: a table that lands the corporate scheme subscriptions unchanged and the load that keeps it up to date, the fixed list of payer types (Individual and Corporate), and the payer type dimension for reporting.
- MOD-005, Invoice line-type mapping and currency: the mapping that says what each invoice item code is for (subscription, concession, readmission fee and so on), to which new item codes are added automatically as 'unmapped'; the list of invoice currencies; and the currency dimension for reporting. This module does not compute any amounts; a later module (MOD-010) does.
- MOD-006, Concession reference and dimension: a table that lands the concession types from the CRM concession reference unchanged and the load that keeps it up to date; the concession type list, which takes in new types and changed names while every type keeps its id, and records for each type its invoice item code and whether it is a full concession and whether it is perpetual; and the concession type dimension for reporting.
- MOD-007, Member-year attributes and new event-table columns: the rule for which invoices count (the eligible invoices) and which one sets a contact's segments for a Campaign Year (the segment invoice); a new table holding, for every contact and every Campaign Year from their first membership event to the current year, their payment method, payer type, corporate scheme number and concession, each flagged where it was carried forward from an earlier year; and the load that keeps it up to date. It also adds the seventeen new segment and amount columns to the two Phase 1 event tables, without filling them: a later module (MOD-012) writes their values, and recording anomalies comes in MOD-008.
- MOD-008, Segment anomalies: a load that records, in the existing Phase 1 anomaly table, four kinds of data problem found with a contact-year's payer type and concession: a Corporate invoice where the contact has no live corporate subscription, an invoice settled both by Corporate and by another method, a concession code that is not in the concession type list, and a Full Concession position whose invoice carries no full-rate concession. It also changes the Phase 1 anomaly load so that it leaves these new kinds of anomaly to their own load.
- MOD-009, Retire silv_payment_events.payment_source: removes the old text column payment_source from the Phase 1 table of paid positions, Layercake.silv_payment_events, because the payer type now lives on the member-year attributes. Nothing else in the table or in its Phase 1 load changes.
- MOD-017, Member status bronze extension: adds two columns to the existing Phase 1 table Layercake.brnz_subs_status, which copies the member invoice statuses from Subs.vwSubsMemberStatuses, one row per contact and Campaign Year: the contact-year's invoiced total in GBP ('Inv Total Amount') and whether its invoices carry a retired concession ('Retired Concession'). It also changes the Phase 1 load of that table so that it fills them. Nothing else in the table or its load changes, and the module builds nothing in silver or gold: later modules use the two columns for the invoiced amount on events (MOD-010) and the derived retirement date (MOD-018).
- MOD-018, Derived retirement date: a view that gives each contact a retirement date taken from the member invoice statuses (the first payment date, or a Full Concession's settlement date, of the earliest Campaign Year whose invoices carry a retired concession), and a change to the Phase 1 load of the member base so that this date replaces the hand-entered retirement date, apuk_retirementdate. Every Phase 1 result that splits members into Practising and Retired then uses it; no other Phase 1 logic changes. It also corrects the Phase 1 events load so that it runs where the database's temporary storage uses a different collation; its event logic is unchanged.
- MOD-010, Event amounts and invoice matching: a new silver table holding one row for every Join, Renewal and Readmission, and the load that keeps it up to date. For each event it records the Campaign Year its amount comes from, its invoiced amount (the contact-year's 'Inv Total Amount', placed on one event per contact and Campaign Year so it is never counted twice) and an amount status that explains every amount, including a missing one. It also pairs each event with its own eligible invoice, for the invoice checks only; no amount is ever taken from the invoices. The module does not write to the event tables or record anomalies: a later module copies the amounts onto the events (MOD-012), and another records the invoice anomalies from the pairing (MOD-011).
- MOD-011, Invoice and readmission anomalies: a load that records, in the existing Phase 1 anomaly table, six kinds of anomaly linking invoices and events, for Campaign Years from 2022: an event with no eligible invoice; an eligible invoice with no event; an event left without an invoice because its contact and Campaign Year has more events than invoices; a surplus invoice because it has more invoices than events; and a Readmission whose invoice carries no readmission fee, recorded as free when the Readmission falls in the second quarter of its Campaign Year and otherwise as having no fee. It works from the pairing of events with invoices that MOD-010 holds and from the invoices' own lines, never from an event amount, and it changes no existing object.

Later modules are added to the pack as they pass testing.
