## ASM-001 · analyst amend spec · unreviewed
**Question:** With the subscription and fee split dropped (Q-038), events keep both subs_amount_gbp and invoiced_subtotal_gbp. Should both hold the same value, the view's 'Inv Total Amount' for the contact and amount Campaign Year? Working default: yes, they are equal. The owner's Invoice_Amount_GBP, which 'Inv Total Amount' sums, already leaves out the RAFEE readmission fee lines and APP lines.
**Why it matters:** The mapping and acceptance values for subs_amount_gbp depend on it, and so do the REQ-014 totals of subscription invoiced.
**Answer:** Yes. Keep your working default. On every Join, Renewal and Readmission event, subs_amount_gbp and invoiced_subtotal_gbp hold the same value: [Inv Total Amount] from the live Layercake.brnz_subs_status row for the event's contact_no and amount Campaign Year. They are null together and carry the same amount_status, including 'Counted on another event' (Q-039) and pre-2022 nulls. Your RULE-035, the subs_amount_gbp mapping ("same value as invoiced_subtotal_gbp"), the A1 and synthetic 0-mismatch ACs, and the REQ-014 AC (both totals 1330.00) can stay as drafted. Record Q-044 as answered by this assumption. Why: Mike's AMD-001 answer (Q-038) says an event's revenue is 'Inv Total Amount'. It drops everything the view cannot supply, including the subscription and fee split, but keeps both subs_amount_gbp and invoiced_subtotal_gbp on the event. The view has no other invoiced-amount column, so they have nothing to differ by. Keeping both columns, rather than dropping one, follows Mike's answer and the columns MOD-007 has already built (silv/fact_membership_events, MIG-0009). That is the smallest change. One correction to your description of the source, so the spec is accurate. In Subs.usp_Refresh_SubsInvoices, Invoice_Amount_GBP is the sum of AMOUNTMST over the invoice's RICINVOICETYPE = 'SUB' lines, with the six RAFEE_* codes excluded. So readmission fee lines and APP lines are not added. Concession lines (negative) are included. Two adjustments apply: (a) if the SUB sum is negative, the amount is 0; (b) otherwise, if the invoice's non-SUB lines (for example APP) net to a negative value, that negative value is added. 'Inv Total Amount' (Subs.usp_Refresh_SubsMemberStatuses) sums Invoice_Amount_GBP over the contact-year's invoices whose Payment_Status is not 'Fully Credited'. Word the spec as "excludes RAFEE readmission fee lines and adds no APP or other non-SUB amount, except where the non-SUB lines net to a credit". Don't say it "leaves out APP lines" outright. The view supplies no fee amount, so subs_amount_gbp is not a subscription-only figure separate from fees. The data pack should say the two columns are equal by design.

## ASM-002 · architect amend design · unreviewed
**Question:** REQ-017 makes the derived retirement date replace silv_member_base.retirement_date wherever Phase 1 sets Practising / Retired. I can't read the Phase 1 source. (1) Which Phase 1 procedures read retirement_date to set membership_status_id? Is it only the loads of silv_membership_events, silv_daily_count_detail and silv_annual_rate_base, or does silv_member_profile.retirement_date carry it between them? (2) silv_daily_count_detail is loaded date by date (etl_daily_count_loaded / etl_daily_count_pending_rebuild). When a contact's retirement date changes, does Phase 1 already register a pending rebuild from the earlier date, and which procedure does that? Working assumption: the three silver loads plus the silv_member_profile load read it, and a change of date registers a pending rebuild through etl_daily_count_pending_rebuild from the earlier of the old and new dates.
**Why it matters:** These names set which Phase 1 procedures the new module changes (its objects and down script). The rebuild behaviour decides whether past daily counts pick up a corrected retirement date, and whether the first run after deployment has to rebuild daily history once.
**Answer:** The Phase 1 code in src/sql/Layercake/Procedures answers both parts. Your working assumption is right about the rebuild being registered, but wrong about which procedures read which table, and wrong to expect the rebuild to happen by itself. (1) Where retirement_date is set and read - It is set in one place only: Layercake.usp_load_silv_member_base. That load is a full re-derive (truncate and insert) and writes `cast(rec.apuk_retirementdate as date) as retirement_date` from the latest brnz_rics_record row (line 316). - Two procedures read silv_member_base.retirement_date directly to set membership_status_id: - Layercake.usp_load_silv_membership_events, in five places: the election-dated events compare it with election_date (lines 321, 376), the Lapse event with lapsed_date (558), and the event_date derivations (749, 887). - Layercake.usp_load_silv_annual_rate_base, which compares it with boundary_date (line 79). - usp_load_silv_daily_count does not read silv_member_base. Its day-level status reads Layercake.silv_member_profile.retirement_date (alias pr, line 446: `iif(pr.retirement_date <= s.[date], 'Retired', 'Practising')`). - silv_member_profile.retirement_date is a diff-synced copy of silv_member_base.retirement_date, made by Layercake.usp_load_silv_member_profile. So yes, the profile carries the date to the daily count, but only to the daily count. Events and annual rates read the base. - Nothing else uses it to set a status: - usp_load_silv_data_anomaly reads silv_member_base but not this column. - recon_active_contact.rr_retirement_date is a reconciliation column. - The gold facts (fact_membership_events, fact_daily_member_count_detail) take membership_status_id from silver and re-sync themselves. Recommendation: make the smallest change. Change only the expression in Layercake.usp_load_silv_member_base that fills silv_member_base.retirement_date. The derived date can come from a new view or function in the new module over brnz_subs_status, which bronze has already landed before silver runs. - That is literally what Mike's answer says: the derived date "replaces apuk_retirementdate (Layercake.silv_member_base.retirement_date)". - Membership events, annual rate base, member profile and daily count then pick it up with no code change. - The module's objects and down script then cover usp_load_silv_member_base plus the new derivation object. The down script restores the Phase 1 definition of usp_load_silv_member_base. - Choosing which objects to change is your design decision. If you instead keep apuk in the base and add a new column, the procedures to change are usp_load_silv_membership_events, usp_load_silv_annual_rate_base and usp_load_silv_member_profile. usp_load_silv_daily_count still needs no change, because it reads the profile. (2) How a changed date reaches the daily count - Yes, Phase 1 registers a pending rebuild. Layercake.usp_load_silv_member_profile does it. - Its diff works out retirement_changed_from as the earlier of the old and new dates, ignoring NULLs (lines 70-71). It then calls `Layercake.usp_etl_log_pending_rebuild @run_id, 'member_profile', @prof_recalc_from` inside its own transaction. - The helper moves the date up to 2020-10-01 if it is earlier, and writes a row only if some date from then on is already in etl_daily_count_loaded. It keeps at most one open row per source, holding the earliest date seen. - It does not rebuild anything. The daily run only loads dates that are not yet marked loaded; the row's detail says "NOT rebuilt by the daily run; use @RebuildFrom to apply". - Past daily counts change only when someone runs `Layercake.usp_load_silver @RebuildFrom = <affected_from>` (or `@FullRebuild = 1`). Step e of usp_load_silv_daily_count then marks the open row as applied. The gold fact_daily_member_count_detail re-syncs itself from silver afterwards. - Events and annual rates correct themselves on the next run: the usp_load_silver header says "events / ranges / rate base always self-correct regardless". What this means for the first run after deployment - The first silver run changes many contacts' dates (apuk to derived, or to NULL with no retired concession from 2022, Q-040). It will register a 'member_profile' pending row, probably from 2020-10-01. - Daily history keeps the old Practising / Retired split until a one-off rebuild is run. Only the status split changes; active, paid and event counts do not (Q-046). - The design should not make the daily run rebuild history automatically. It should state the one-off `usp_load_silver @RebuildFrom` (or `@FullRebuild = 1`) after the first run as a step in the deployment and handover. Running it on the live database is a human step, like the other handover steps.
**Basis:** src/sql/Layercake/Procedures/Layercake.usp_load_silv_member_base.sql line 316 (retirement_date from apuk_retirementdate; full re-derive); src/sql/Layercake/Procedures/Layercake.usp_load_silv_membership_events.sql lines 321, 376, 558, 749, 887; src/sql/Layercake/Procedures/Layercake.usp_load_silv_annual_rate_base.sql line 79; src/sql/Layercake/Procedures/Layercake.usp_load_silv_daily_count.sql line 446 (reads silv_member_profile), header 'retrospective changes are logged by the producing modules, not applied here', step e; src/sql/Layercake/Procedures/Layercake.usp_load_silv_member_profile.sql lines 70-71, 131 (pending rebuild 'member_profile'); src/sql/Layercake/Procedures/Layercake.usp_etl_log_pending_rebuild.sql (clamp to 2020-10-01, only when loaded dates are affected, one open row per source); src/sql/Layercake/Procedures/Layercake.usp_load_silver.sql header (@RebuildFrom; events/ranges/rate base self-correct); src/sql/Layercake/Procedures/Layercake.usp_load_fact_daily_member_count_detail.sql (gold re-syncs from silver); docs/answers.md Revenue and retirement sources (derived date replaces silv_member_base.retirement_date); Q-040; Q-046
