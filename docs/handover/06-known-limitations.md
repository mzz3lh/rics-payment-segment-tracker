# Known limitations: RICS Payment Segment Tracker

## Assumptions awaiting confirmation

These are working assumptions recorded in the specification and design, each awaiting the client's answer to an open question. The MOD-001 corporate status profile exists to help answer the first, Q-027. The grain of the invoice line source (Q-021) is no longer an assumption: it was answered from real data on 2026-11-11 (see Known limitations).

## Known limitations

- **The invoice lines are now at the source's real grain, and the loads that read them are retested at it only in a later module.** The question of the grain of synapse_fo.CUSTTRANS_RICS (Q-021) was answered from real data, with counts only, on 2026-11-11. The working assumption had been one row per invoice line; in fact each customer transaction is split into one row per ledger distribution (posting type and ledger account string), and 458,563 transactions are split across 1,015,865 rows. Before MOD-019, the invoice line load failed on such data. MOD-019 now lands every row that belongs to an invoice, unchanged and never added together, and the rules that depended on Q-021 keep CUSTTRANS_RICS as their source, read at this grain. By design, the line-type mapping, the fee-only test on eligible invoices, the concession choice, the double payment and unknown concession code anomalies, the readmission fee check and the invoice-with-no-event anomaly need no change at the new grain. They are retested at it in a later module (MOD-020), which has not yet been delivered.
- **Until MOD-020 is delivered, the payment-line fallback can count a split payment more than once.** Where a segment invoice has no payment mode, the member-year attributes load adds up the settled amounts of the payments that settle it, per payment method (RULE-013). A payment's settled amount belongs to the whole payment and is repeated on each of its lines, so a payment split across several lines is added once per line, and weighs more than it should when the payment methods are compared. The design records this as the one reader that adds up a transaction-level value per line; MOD-020 changes it so that each payment counts once (RULE-105).
- **The first invoice line load after MIG-0019 replaces the landed lines.** Rows landed before the change have no ledger columns, so the first run of the line load afterwards marks them all as deleted and adds the source rows at the new grain; the old rows stay in the table, marked as deleted. The one exception is a source row with no posting type and no ledger account string, which updates its old row in place. This happens once, and the load log shows the old rows as deleted and the new ones as inserted.
- **Rolling back MOD-019 on a table that holds rows sets those rows aside.** Because a recid can appear on several rows at the new grain, the old key cannot hold them. When the table holds rows, the rollback renames it, with its keys, to brnz_subs_invoice_line_rolledback_MIG0019, creates an empty table in its MOD-002 shape and restores the MOD-002 load, which then lands the table again and, on real data, fails on split transactions as it did before. When the table is empty, the rollback simply changes it back. This goes beyond the project's usual rule that a table's change script only alters that table; the design asks for it. The automated rollback test covered the empty table; the rollback of a table holding rows was checked separately on the development database, where it worked as expected.
- **A repeated invoice line identity stops the whole invoice line load.** Two rows of synapse_fo.CUSTTRANS_RICS in scope with the same transaction, posting type and ledger account string fail the load, as the design sets; no row is skipped. Values that differ only in letter case or trailing spaces count as the same, as the database compares them, and so do two rows of one transaction that both have no posting type and no ledger account string. The load changes nothing, so brnz_subs_invoice_line keeps the data from its last successful run until the source's owner corrects the data and the load is run again (see the Runbook).
- **Two indexes that the design lists for the invoice line table do not exist.** The design's performance notes say the table keeps indexes on account number and voucher, and on last settlement voucher, "as before". Neither the table built by MOD-002 nor the development database has them, so MOD-019 did not add them; adding them was outside its scope. Please decide whether they should be added.
- **The event columns are current only after the two event column loads have run.** As ADR-001 recommends, the segments and amounts are written onto the event tables by two loads that run after the Phase 1 run (MOD-012). The Phase 1 loads do not write these columns, so an event that the Phase 1 run adds holds the defaults (Unknown, 0, for payment method, payer type and concession, 0 for the carried flags, and no amounts) until the silver and then the gold event column loads next run. Until the run procedure (MOD-016) is delivered, those loads are run by hand, so new events should not be reported on by segment or amount until they have run. A Join, Renewal or Readmission that has no row in the event amounts table when the silver event column load runs gets no amount and no amount status, replacing any it held; this is why the event amount load runs before the event column loads (see the Runbook).
- **An event's amount is its contact-year's total, with no split.** Under the amended specification (Q-038), the amount is the member invoice statuses' Inv Total Amount for the contact and Campaign Year, placed whole on one event; any other Join, Renewal or Readmission in the same contact-year has no amount and the status 'Counted on another event'. There is no subscription and fee split, no amount in the invoice currency, no currency, no credited amount and no net amount, so MOD-012 removes those eight columns from the event tables, and the currency list and dimension (REQ-007) describe no event amount. As recorded under Q-044, subs_amount_gbp holds the same value as invoiced_subtotal_gbp by design: it is not a subscription-only figure separate from fees.
- **Invoice data starts at Campaign Year 2022.** The invoice source, Subs.tblSubsInvoices, keeps only Campaign Year 2022 onward, so the bronze invoice tables hold nothing earlier, and contact-years before 2022, and their events, show Not applicable for payment method, payer type and concession (assumed, Q-011).
- **Some carry-forward and tie-break behaviours were decided during the build, not by the design.** They follow the wording of the specification and are awaiting confirmation:
  - Where the latest earlier invoiced year got Unknown (0) for payment method or payer type, a later year with no invoice carries that Unknown, with its carried flag set to 1. The alternative would be Unknown with flag 0. So a carried flag of 1 does not always mean a known value was carried.
  - An eligible invoice from 2022 onward in a year before the contact's first membership event can be carried into the first and later years, because carrying looks at all the contact's segment invoices from 2022, not only the years that have a row.
  - A double payment (Corporate and another method) where the contact has no live corporate subscription is Individual even when the contact has no Phase 1 paid position, following RULE-026 ('otherwise Individual'). 'Another method' includes an unrecognised payment mode.
  - In the payment-line fallback, a payment method whose lines all have no transaction date loses a tie on the earliest payment to any dated method.
  - Where a segment invoice carries several concession lines, a code that is in the concession type list beats one that is not; among known codes the highest discount wins, then the line with the lowest row key. The year is Unrecognised only when none of its concession lines is known.
- **Two event amount behaviours were decided during the build, not by the design.** Please confirm these are acceptable:
  - A Join takes its amount, and its paired invoice, from the contact's earliest paid position, even when that year is earlier than the Join's own Campaign Year. This follows RULE-032 as written ('the Campaign Year of the contact's first paid position'). The event column load uses the same rule for the Join's segments (MOD-012), so such a Join also carries that earlier year's payment method, payer type and concession.
  - Two tie-breaks can point to different events. When events outnumber invoices and two events of the same type have the same date, the invoice goes to the event whose identifier text (event_nk) comes first (Q-036); the amount, between two such events, goes to the event with the lowest event_id (Q-047). So the event that carries the amount is not always the one paired with the invoice.
- **An Inv Total Amount too large for the event amount columns stops the event amount load.** The event amounts hold up to 15 digits before the decimal point and 4 after, the type of the event tables' amount columns, while brnz_subs_status keeps the source's full size (up to 32 digits before the decimal point). A larger value fails the whole event amount load, which changes nothing, rather than storing a cut-down amount; the fix goes to the owner of Subs.vwSubsMemberStatuses (see the Runbook).
- **Segment and invoice anomaly rows show only the current cases.** The Phase 1 anomaly types are kept when they stop being detected, marked as resolved, and re-opened if they recur. The four segment and six invoice anomaly types work differently, as the design sets: a case that no longer applies, for example after a corrected invoice, is removed by the next run of its load. So silv_data_anomaly keeps no history of segment or invoice cases that have been put right, and on these rows both first_detected_at and last_seen_at show when the case was first recorded; later runs do not refresh last_seen_at.
- **A Full Concession year with no segment invoice is not a segment anomaly.** As confirmed on 2026-11-06, FULL_CONCESSION_NO_CONCESSION is raised only where the year's segment invoice exists but carries no full-rate concession. A Full Concession year with no segment invoice is left to the invoice anomaly EVENT_NO_INVOICE (MOD-011), so the same gap is not counted twice.
- **Some segment anomaly behaviours were decided during the build, not by the design.** Please confirm these are acceptable:
  - The design says cases that still apply are left untouched. The load does leave them untouched while the data is unchanged, but when the text of a case's detail changes, for example because the year's segment invoice is now a different invoice, it rewrites the detail so that it always names the current segment invoice. It keeps the case's first-detected and last-seen times, and counts the change as an update in the load log.
  - A concession code that is not in the concession type list raises CONCESSION_NOT_IN_REFERENCE even when another concession line on the same invoice is known and sets the year's concession.
  - The anomaly key (anomaly type, contact number, Campaign Year and, for an unknown concession code, the code) must fit the table's key column, which holds up to 240 characters. A key that does not fit stops the whole segment anomaly load, which changes nothing (see the Runbook).
- **Some invoice anomaly behaviours were decided during the build, not by the design.** Please confirm these are acceptable:
  - A Readmission whose Campaign Year has no row in the Campaign Year table, Layercake.ref_campaign_year_config, has no free-readmission window, so if its invoice has no readmission fee line it gets READMISSION_NO_FEE, never READMISSION_FREE.
  - A paired invoice that is no longer live has no own lines, so its Readmission counts as having no readmission fee line.
  - As for the segment anomalies, a case that still applies is rewritten when the text of its detail changes, for example when the paired invoice's number changes, keeping its first-detected and last-seen times and counting as an update in the load log.
- **An unusually long event identifier would stop the invoice anomaly load.** The anomaly key holds up to 240 characters. For an anomaly about an event it is the anomaly type, a colon and the event's identifier text (event_nk); the longest type takes 32 characters, so an identifier longer than 208 characters would not fit. The load then fails and changes nothing, rather than shortening the key (see the Runbook). Phase 1 event identifiers are short, for example 'RN:' followed by the contact number and year, so this is not expected in real data; it was recorded during the build as a data risk.
- **Two change scripts for silv_data_anomaly make no change.** The delivery includes src/sql/changes/MOD-008/Layercake.silv_data_anomaly.up.sql and its matching .down.sql, left from an earlier stage of the build. Each only re-checks the table's existing constraints and changes nothing. As agreed on 2026-11-06, no change script should exist for this table, whose structure MOD-008 does not change; the two files remain until a person removes them. The rollback test passed with them in place.
- **The Phase 1 payment events load was not changed, although the module plan said it would be.** The plan for MOD-009 was to change the Phase 1 load of silv_payment_events, Layercake.usp_load_silv_payment_events, so that it stopped writing payment_source. As confirmed on 2026-11-06 (Q-031), that load never wrote the column, which only took its default, so it is left exactly as it was and only the table changes. For the client this means no Phase 1 load changes in this module, and the tests confirmed the load behaves as before.
- **Rolling back MOD-009 sets payment_source to 'Individual' on every row.** The rollback script adds the column back with its default, 'Individual', so every existing row of silv_payment_events gets that value. This was the only value the column could ever hold, because the Phase 1 load never wrote it, so the rollback restores both the column and its contents.
- **The payment events table keeps its Phase 1 key name.** The key of silv_payment_events, pk_silv_payment_events, does not follow the project's naming standard for keys. It is kept as it is, because MOD-009 changes nothing in the table except removing payment_source. This affects only the name, not any result.
- **The changed Phase 1 objects keep their Phase 1 style and names.** MOD-017 changes Layercake.brnz_subs_status and Layercake.usp_load_brnz_subs_status as little as the new columns need, so both keep the Phase 1 code layout and the Phase 1 names of the table's key and defaults, which do not follow the project's coding and naming standard. MOD-018 likewise keeps the Phase 1 code layout of the member base and events loads it changes. This affects only how the code is laid out and named, not any result.
- **The first member status load after MOD-017 is deployed updates every row.** The two new columns of brnz_subs_status start empty, so the first run of the member status load afterwards fills them on every live row and records them all as updated, with a new _updated_at on each. This is expected and happens once; after that, only rows whose source values change are updated.
- **The member status load does not stop on incomplete or repeated source rows.** Unlike the new bronze loads, the Phase 1 member status load, which MOD-017 changes only to land two more columns, keeps its Phase 1 handling of such rows: a source row with no contact number or no Campaign Year is not landed, and where Subs.vwSubsMemberStatuses has two rows for the same contact and Campaign Year, only the one with the latest Renewal Date Adj is landed, with its own Inv Total Amount and Retired Concession. The load does not fail in either case.
- **Results split by Practising / Retired change.** As agreed on 2026-11-06 (Q-046), the derived retirement date replaces the hand-entered apuk_retirementdate (MOD-018, REQ-017), so every Phase 1 result split by membership status changes: membership events, annual rates and daily counts. Active, paid and event counts by date, region and grade do not change, and the Phase 1 difference scripts are to still pass. The full before-and-after comparison of Phase 1 results, including those scripts, comes in MOD-016.
- **Members who retired before 2022 show as Practising until their first retired-concession year from 2022.** The member invoice statuses hold invoice data from Campaign Year 2022, and, as agreed on 2026-11-06 (Q-040), there is no fallback to apuk_retirementdate or to 'First Retired Year'. So a member who retired earlier is Practising until their first year from 2022 whose invoices carry a retired concession, and a member with no such year is never Retired because of a retirement date, whatever the CRM record says.
- **The hand-entered retirement date is no longer in the member base.** Under ADR-005, silv_member_base.retirement_date now holds the derived date, so apuk_retirementdate is no longer visible in silver. It is still in the bronze CRM record table, brnz_rics_record, and, as confirmed on 2026-11-09 (Q-048), the reconciliation scripts' diagnostic columns still show it; their pass checks by region and grade are not affected. As confirmed on 2026-11-11, the retirement comparison (MOD-013) does not compare the hand-entered date with the derived date either: it compares the retired concession with the derived date only.
- **Past daily counts keep the old Practising / Retired split until a one-off rebuild.** The daily run loads only days not yet loaded, so days loaded before MIG-0013 keep the split from apuk_retirementdate. Membership events and the annual rate base correct themselves on the next Phase 1 run, past Campaign Years included, but daily history changes only when a person runs the one-off rebuild described in the Runbook; the design adds no automatic rebuild. The rebuild recomputes the daily counts from 1 October 2020, the heaviest step the amendment adds, so it is run outside the daily window.
- **The Phase 1 events load is also changed, for a technical reason only.** The design changes four Phase 1 procedures. The Phase 1 events load, Layercake.usp_load_silv_membership_events, failed with a collation error (error 468) wherever tempdb's collation differs from the database's. As agreed on 2026-11-09, MOD-018 also changes this load, only to give its working table the database's collation. Its event logic is unchanged and testing confirmed its results, so this affects no result. Rolling back MOD-018 restores the Phase 1 definition of the load.
- **Very large invoice amounts would stop the invoice load.** The money columns of brnz_subs_invoice hold up to 26 digits before the decimal point, which is the solution's standard money type, while the source allows up to 32. This is the one deliberate exception to copying source column sizes exactly, confirmed on 2026-10-26, since no real invoice amount comes near that size. If such a value ever appeared, the load would fail and change nothing (see the Runbook) rather than store a cut-down amount.
- **Payments and credits posted on another customer account are not landed.** A transaction row is landed against an invoice only when it is on the invoice's own account. A payment or credit that settles the invoice but was posted on a different account is left out, as confirmed on 2026-10-26, so it also plays no part in the payment-line fallback for payment method or in the double payment anomaly.
- **One incomplete or repeated corporate subscription row stops the whole corporate subscription load.** A source row with no contact number, scheme number or Campaign Year fails the load, as confirmed on 2026-10-26; the row is not skipped. Two source rows with the same contact number, scheme number and Campaign Year also fail it (built on the Q-033 assumption above), rather than one of them being landed at random. In either case the load changes nothing, so the table keeps the data from the last successful run until the source is corrected by its owner and the load is run again (see the Runbook).
- **One incomplete or repeated concession type stops the whole concession bronze load.** A row of CE.vwConcessionType with no concession type id (apuk_concessiontypeid), or two rows with the same id, fails the load, as confirmed on 2026-10-27; no row is skipped. The load changes nothing, so brnz_concession keeps the data from the last successful run until the source's owner corrects it and the load is run again (see the Runbook).
- **A concession type with no name is listed as 'Unnamed concession type'.** As confirmed on 2026-10-27, a type whose name is missing, empty or only spaces is still added to the concession type list, with its id, item code and flags, under the name 'Unnamed concession type', so the invoices that use it are not lost. When the source later gives it a name, the next load puts that name in place on the same id.
- **Most item codes will need mapping by hand.** As confirmed on 2026-10-27 (Q-034), the line-type mapping starts with only the 12 item codes that the existing Subs.usp_Refresh_SubsInvoices names; no other curated list exists. The first load adds every other item code, the subscription codes included, as 'unmapped'. After the first load on real data, Damian maps the unmapped codes by hand, following how Subs.usp_Refresh_SubsInvoices classifies them: a line of RIC invoice type 'SUB' whose code is in the concession product list is a concession, other 'SUB' lines are subscription, and RIC invoice type 'APP' is an enrolment or application fee. The member-year attributes use the mapping to recognise invoices that carry only an enrolment or application fee, and a line with no mapping counts as unmapped. The readmission fee check (MOD-011) also reads the line types: a fee is recognised only by the line type 'readmission fee', so a Readmission whose invoice carries a fee code not mapped as 'readmission fee' is recorded as having no fee (READMISSION_FREE or READMISSION_NO_FEE). Under the amended specification, line types no longer affect any event amount, and 'Unmapped lines' is no longer an amount status (RULE-030). New codes that appear later arrive as 'unmapped' in the same way.
- **A wrong starting row can only be corrected by hand.** The line-type mapping load never changes an existing row, so that hand mappings are kept. The same applies to the 12 starting rows: if one is wrong, a person must correct it in the table.
- **Which spelling is stored for a new code was decided during the build.** When a new item code or currency arrives in several spellings in the same load (differing only in letter case or trailing spaces), one row is added and the same spelling is kept on every run: upper case first, then the one without trailing spaces. The design does not say which spelling to keep. Please confirm this is acceptable.
- **Two concession types could share one item code.** Nothing in the concession type list stops two live source types from carrying the same item code. The member-year attributes match the concession lines on an invoice to the concession types by item code, so such a code does not point to a single type: the load picks one of them by the concession tie-break above rather than failing. This was recorded during the build as a data risk.
- **Some concession type list behaviours were decided during the build, not by the design.** An 'rcs' prefix is removed from the product number whatever its letter case, and only at the start of the code. An item code longer than 100 characters stops the concession type list load, which changes nothing, rather than storing a cut-down code (the source product number can be up to 4,000 characters). The four starting rows (the three reserved values and 'No concession') are never changed by the load, and a type that leaves the source keeps its row in the list unchanged. Please confirm these are acceptable.
- **The event columns are not linked to the lists by database keys.** Neither Phase 1 event table has database keys, and a key to the payment method dimension would stop the Phase 1 fact load while that dimension is empty, so none was added. The database itself therefore does not check that each event's payment method, payer type and concession is in its dimension. Testing confirmed that the event column loads write only values that are, in silver and in gold (AC-005-02, AC-006-09, AC-011-08). The member-year attributes table does have keys to its three silver lists.
- **The fixed values the attributes load relies on are held in one place in the load.** They are the ids of Corporate (payment method), Individual and Corporate (payer type) and No concession, the first invoice year 2022 (Q-011) and the active status 'Active' (Q-027). If Q-011 or Q-027 is answered differently, that one place changes.
- **The layout of the profiles' results is not yet confirmed.** The design does not define it, and the question about it is still unanswered. The profiles were built and tested to the layout described in the Architecture and data model document. If a different layout is wanted, the procedures and their tests will need to change.
- **Some edge cases in the grain profile were decided during the build, not by the design.** Rows with no transaction type or no invoice number are not treated as invoice rows and are left out. A row with no item code adds nothing to the count of different item codes. A tax row is recognised only by the posting type 'Sales tax'. Please confirm these suit the purpose of the profile.
- **The layout of the retirement comparison's result was set during the build, not by the design.** The design does not define the report's parameters or result. It was built and tested with one optional as-of date, which it accepts but does not use, and one row per Campaign Year that has at least one paid position, with seven columns: the Campaign Year, the number of paid positions, the four group counts and the agreement rate as a percentage to one decimal place (70.0 meaning 70.0%), as described in the Architecture and data model document. If a different layout is wanted, the procedure and its tests will need to change.
- **Some retirement comparison behaviours were decided during the build, not by the design.** Please confirm these are acceptable:
  - A derived retirement date counts only when it is on or before that Campaign Year's end, in every group. So a paid position with no retired concession whose derived date falls after the year end, meaning the contact first retired in a later Campaign Year, is counted under 'neither' and counts towards agreement, just as a retired concession with such a date counts as 'retired concession only'.
  - A paid position with no member-year attributes row for its Campaign Year counts as having no retired concession.
  - An item code that differs from one of the six retired codes only in letter case counts as retired.
- **A paid position in a Campaign Year missing from the Campaign Year table cannot have its derived date counted.** If a paid position's Campaign Year has no row in Layercake.ref_campaign_year_config, the retirement comparison still counts the position in its year, but its derived date cannot be compared with a year end, so it is counted as having no derived date. The design does not cover this case. It should not arise, because every Phase 1 silver run adds any missing Campaign Year to that table.
- **No employer segment is built in this release.** As agreed (Q-020), REQ-013 is delivered as findings only: no employer landing, grouping, key or dimension is built and no employer column is added (RULE-059), so membership events and paid members cannot be filtered by employer. Full employer segmentation is planned for early 2027. The three employer findings reports (MOD-014) give the evidence for that work (see the employer data quality note below).
- **The employer on the CRM contact record has not yet been checked on real data.** The specification left the contact-record employer field to be identified during discovery. It was set during the build as the parent account on the CRM contact record (CE.vwContact.ParentCustomerId, where that parent is an account), and the two sources are matched on the scheme's organisation (apuk_onbehalfoforganisationid). The development copies of the CRM views hold no data, so whether this field is filled in on real contact records needs checking when Mike first runs the reports. Please confirm the field.
- **The layout of the employer reports' results was set during the build, not by the design.** The design describes each report in one line. They were built and tested with the parameters and columns described in the Architecture and data model document; the coverage percentages and the top 25 were confirmed on 2026-11-11. If a different layout is wanted, the procedures and their tests will need to change.
- **Some employer report behaviours were decided during the build, not by the design.** Please confirm these are acceptable:
  - In the top-employers list, a Corporate member with live subscriptions to schemes of more than one firm counts once, under the scheme with the lowest scheme number (then the lowest account number); a contact with more than one contact-record firm counts under the lowest account number; and where the two sources give one account number different names, the name that comes last alphabetically is shown.
  - On a tie at 25th place, the firm with the lower account number is listed. The tie-break by account number was confirmed on 2026-11-11; which way it runs was set during the build.
  - In the agreement report, a member with more than one scheme firm or contact-record firm in a year counts as same firm when any of them match; only a scheme with an account number counts as a source; and a Campaign Year in which no member has both sources gives no row.
  - In the coverage report, the scheme link is checked for every payer type, so an Individual member with a live corporate subscription is counted under scheme_link_employer; and a paid year with no member-year attributes row is reported under Unknown.
  - The coverage and agreement reports accept the as-of date but do not use it, and report every Campaign Year. The top-employers report stops with an error, rather than returning an empty list, when no Campaign Year covers the as-of date or none comes before it.
- **Only spaces are ignored around a payment mode code.** The mapping ignores letter case and spaces before or after a code, as confirmed on 2026-10-26. Other characters were decided during the build: a tab or a line break around a code, or a space inside it, makes the code Unrecognised. Such a code would show as Unrecognised rather than as its method. Please confirm this is acceptable.
- **The dimensions never remove a row.** This was decided during the build: the design says only that each load copies its list. An id taken out of a list would stay in its dimension (payment method, payer type, currency or concession type), because reporting data may still point to it. The payment method and payer type lists are fixed, and the currency and concession type lists never remove a row, so in practice their ids stay in place.
- **The permission scripts need the analyst's role name.** The grant scripts for the profiles (src/sql/grants/MOD-001.sql), the retirement comparison (src/sql/grants/MOD-013.sql) and the employer reports (src/sql/grants/MOD-014.sql) use the placeholder [<analyst_role>], because the role name is not known. They cannot be run until a person replaces the placeholder.
- **The decision records for ADR-001, ADR-002, ADR-003, ADR-004, ADR-005 and ADR-006 are still marked as pending**, although the design that follows their recommendations has been approved. ADR-002 also still describes the amounts as coming from the invoices, as they did before the specification was amended; the design itself takes them from the member invoice statuses. ADR-004's main text still describes the window as an open choice; its addendum of 2026-11-10 records the agreed answer, the second quarter of the Campaign Year (Q-032). ADR-006 is still a proposal: MOD-019 is built on its recommended option, a technical row number as the primary key with the invoice line identity enforced separately, and if another option is chosen, the invoice line table, its change script and the test of its keys change. The identity is enforced by a unique constraint rather than a separately created unique index; the database enforces it in the same way.

### Employer data quality note

The specification asks for an employer data quality note (AC-013-05) giving the coverage of the two employer sources by Campaign Year and payer type, the agreement rate between them, and a recommendation to build the employer segment or not. The reports that produce its figures are delivered and have passed testing on synthetic data, but they have not yet been run on real data, so the note's figures and its recommendation are still to be confirmed.

Once Mike runs the three reports on real data, the note takes its figures from them:

| What the note reports | Where it comes from |
|---|---|
| Coverage of each employer source, by Campaign Year and payer type | Layercake.usp_report_employer_scheme_coverage: scheme_link_coverage_pct and contact_record_coverage_pct on each row, with no_employer for the members with neither |
| The agreement rate between the two sources, by Campaign Year | Layercake.usp_report_employer_source_agreement: agreement_rate_pct, over the members with an employer from both sources |
| The paid members left out of the top-employers list because their payer type is Unknown | The Unknown row of the coverage report (paid_members), as confirmed on 2026-11-11 |
| The largest employers in the last full Campaign Year | Layercake.usp_report_top_employers |

Testing confirmed that these figures agree across the reports: the Unknown row of the coverage report is the number left out of the top-employers list, and each firm's counts in that list are its Corporate and Individual members with a firm (TC-014-016).

What is already known about the two sources before the real-data run:

- A scheme link gives an employer only where the scheme's CRM row has an account number, and only for a subscription that is live for the Campaign Year, which rests on the assumption that 'Active' means live (Q-027, see above).
- Whether the parent account on the CRM contact record is filled in on real records has not yet been checked (see above).

How to run: after the corporate subscription load, the member-year attributes load and the Phase 1 run have run on real data, run each report with no parameters (all three take an optional @as_of_date, which only the top-employers report uses), for example:

```sql
exec Layercake.usp_report_employer_scheme_coverage;
exec Layercake.usp_report_employer_source_agreement;
exec Layercake.usp_report_top_employers;
```
