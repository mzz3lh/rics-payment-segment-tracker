## Known limitations

- **The new event columns hold placeholders until later modules fill them.** MOD-007 adds the seventeen segment and amount columns to silv_membership_events and fact_membership_events but writes no values. Until the loads that fill them are delivered (MOD-012, with the amounts from MOD-010), every event shows Unknown (0) for payment method, payer type and concession, 0 for the carried flags, and no amounts. These are defaults, not results, so the new event columns should not be reported on yet. The segments themselves are already available per contact and Campaign Year in silv_member_year_attributes.
- **Invoice data starts at Campaign Year 2022.** The invoice source, Subs.tblSubsInvoices, keeps only Campaign Year 2022 onward, so the bronze invoice tables hold nothing earlier, and contact-years before 2022 show Not applicable for payment method, payer type and concession (assumed, Q-011).
- **Some carry-forward and tie-break behaviours were decided during the build, not by the design.** They follow the wording of the specification and are awaiting confirmation:
  - Where the latest earlier invoiced year got Unknown (0) for payment method or payer type, a later year with no invoice carries that Unknown, with its carried flag set to 1. The alternative would be Unknown with flag 0. So a carried flag of 1 does not always mean a known value was carried.
  - An eligible invoice from 2022 onward in a year before the contact's first membership event can be carried into the first and later years, because carrying looks at all the contact's segment invoices from 2022, not only the years that have a row.
  - A double payment (Corporate and another method) where the contact has no live corporate subscription is Individual even when the contact has no Phase 1 paid position, following RULE-026 ('otherwise Individual'). 'Another method' includes an unrecognised payment mode.
  - In the payment-line fallback, a payment method whose lines all have no transaction date loses a tie on the earliest payment to any dated method.
  - Where a segment invoice carries several concession lines, a code that is in the concession type list beats one that is not; among known codes the highest discount wins, then the line with the lowest row key. The year is Unrecognised only when none of its concession lines is known.
- **Segment anomaly rows show only the current cases.** The Phase 1 anomaly types are kept when they stop being detected, marked as resolved, and re-opened if they recur. The four segment anomaly types work differently, as the design sets: a case that no longer applies is removed by the next run of the segment anomaly load. So silv_data_anomaly keeps no history of segment cases that have been put right, and on a segment row both first_detected_at and last_seen_at show when the case was first recorded; later runs do not refresh last_seen_at.
- **A Full Concession year with no segment invoice is not a segment anomaly.** As confirmed on 2026-11-06, FULL_CONCESSION_NO_CONCESSION is raised only where the year's segment invoice exists but carries no full-rate concession. A Full Concession year with no segment invoice is recorded once, as the invoice anomaly EVENT_NO_INVOICE, which comes in a later module (MOD-011).
- **Some segment anomaly behaviours were decided during the build, not by the design.** Please confirm these are acceptable:
  - The design says cases that still apply are left untouched. The load does leave them untouched while the data is unchanged, but when the text of a case's detail changes, for example because the year's segment invoice is now a different invoice, it rewrites the detail so that it always names the current segment invoice. It keeps the case's first-detected and last-seen times, and counts the change as an update in the load log.
  - A concession code that is not in the concession type list raises CONCESSION_NOT_IN_REFERENCE even when another concession line on the same invoice is known and sets the year's concession.
  - The anomaly key (anomaly type, contact number, Campaign Year and, for an unknown concession code, the code) must fit the table's key column, which holds up to 240 characters. A key that does not fit stops the whole segment anomaly load, which changes nothing (see the Runbook).
- **Two change scripts for silv_data_anomaly make no change.** The delivery includes src/sql/changes/MOD-008/Layercake.silv_data_anomaly.up.sql and its matching .down.sql, left from an earlier stage of the build. Each only re-checks the table's existing constraints and changes nothing. As agreed on 2026-11-06, no change script should exist for this table, whose structure MOD-008 does not change; the two files remain until a person removes them. The rollback test passed with them in place.
- **The Phase 1 payment events load was not changed, although the module plan said it would be.** The plan for MOD-009 was to change the Phase 1 load of silv_payment_events, Layercake.usp_load_silv_payment_events, so that it stopped writing payment_source. As confirmed on 2026-11-06 (Q-031), that load never wrote the column, which only took its default, so it is left exactly as it was and only the table changes. For the client this means no Phase 1 load changes in this module, and the tests confirmed the load behaves as before.
- **Rolling back MOD-009 sets payment_source to 'Individual' on every row.** The rollback script adds the column back with its default, 'Individual', so every existing row of silv_payment_events gets that value. This was the only value the column could ever hold, because the Phase 1 load never wrote it, so the rollback restores both the column and its contents.
- **The payment events table keeps its Phase 1 key name.** The key of silv_payment_events, pk_silv_payment_events, does not follow the project's naming standard for keys. It is kept as it is, because MOD-009 changes nothing in the table except removing payment_source. This affects only the name, not any result.
- **The changed Phase 1 objects keep their Phase 1 style and names.** MOD-017 changes Layercake.brnz_subs_status and Layercake.usp_load_brnz_subs_status as little as the new columns need, so both keep the Phase 1 code layout and the Phase 1 names of the table's key and defaults, which do not follow the project's coding and naming standard. MOD-018 likewise keeps the Phase 1 code layout of the member base and events loads it changes. This affects only how the code is laid out and named, not any result.
- **The first member status load after MOD-017 is deployed updates every row.** The two new columns of brnz_subs_status start empty, so the first run of the member status load afterwards fills them on every live row and records them all as updated, with a new _updated_at on each. This is expected and happens once; after that, only rows whose source values change are updated.
- **The member status load does not stop on incomplete or repeated source rows.** Unlike the new bronze loads, the Phase 1 member status load, which MOD-017 changes only to land two more columns, keeps its Phase 1 handling of such rows: a source row with no contact number or no Campaign Year is not landed, and where Subs.vwSubsMemberStatuses has two rows for the same contact and Campaign Year, only the one with the latest Renewal Date Adj is landed, with its own Inv Total Amount and Retired Concession. The load does not fail in either case.
- **Results split by Practising / Retired change.** As agreed on 2026-11-06 (Q-046), the derived retirement date replaces the hand-entered apuk_retirementdate (MOD-018, REQ-017), so every Phase 1 result split by membership status changes: membership events, annual rates and daily counts. Active, paid and event counts by date, region and grade do not change, and the Phase 1 difference scripts are to still pass. The full before-and-after comparison of Phase 1 results, including those scripts, comes in MOD-016.
- **Members who retired before 2022 show as Practising until their first retired-concession year from 2022.** The member invoice statuses hold invoice data from Campaign Year 2022, and, as agreed on 2026-11-06 (Q-040), there is no fallback to apuk_retirementdate or to 'First Retired Year'. So a member who retired earlier is Practising until their first year from 2022 whose invoices carry a retired concession, and a member with no such year is never Retired because of a retirement date, whatever the CRM record says.
- **The hand-entered retirement date is no longer in the member base.** Under ADR-005, silv_member_base.retirement_date now holds the derived date, so apuk_retirementdate is no longer visible in silver. It is still in the bronze CRM record table, brnz_rics_record, and, as confirmed on 2026-11-09 (Q-048), the reconciliation scripts' diagnostic columns still show it; their pass checks by region and grade are not affected.
- **Past daily counts keep the old Practising / Retired split until a one-off rebuild.** The daily run loads only days not yet loaded, so days loaded before MIG-0013 keep the split from apuk_retirementdate. Membership events and the annual rate base correct themselves on the next Phase 1 run, past Campaign Years included, but daily history changes only when a person runs the one-off rebuild described in the Runbook; the design adds no automatic rebuild. The rebuild recomputes the daily counts from 1 October 2020, the heaviest step the amendment adds, so it is run outside the daily window.
- **The Phase 1 events load is also changed, for a technical reason only.** The design changes four Phase 1 procedures. The Phase 1 events load, Layercake.usp_load_silv_membership_events, failed with a collation error (error 468) wherever tempdb's collation differs from the database's. As agreed on 2026-11-09, MOD-018 also changes this load, only to give its working table the database's collation. Its event logic is unchanged and testing confirmed its results, so this affects no result. Rolling back MOD-018 restores the Phase 1 definition of the load.
- **Very large invoice amounts would stop the invoice load.** The money columns of brnz_subs_invoice hold up to 26 digits before the decimal point, which is the solution's standard money type, while the source allows up to 32. This is the one deliberate exception to copying source column sizes exactly, confirmed on 2026-10-26, since no real invoice amount comes near that size. If such a value ever appeared, the load would fail and change nothing (see the Runbook) rather than store a cut-down amount.
- **Payments and credits posted on another customer account are not landed.** A transaction row is landed against an invoice only when it is on the invoice's own account. A payment or credit that settles the invoice but was posted on a different account is left out, as confirmed on 2026-10-26, so it also plays no part in the payment-line fallback for payment method or in the double payment anomaly.
- **One incomplete or repeated corporate subscription row stops the whole corporate subscription load.** A source row with no contact number, scheme number or Campaign Year fails the load, as confirmed on 2026-10-26; the row is not skipped. Two source rows with the same contact number, scheme number and Campaign Year also fail it (built on the Q-033 assumption above), rather than one of them being landed at random. In either case the load changes nothing, so the table keeps the data from the last successful run until the source is corrected by its owner and the load is run again (see the Runbook).
- **One incomplete or repeated concession type stops the whole concession bronze load.** A row of CE.vwConcessionType with no concession type id (apuk_concessiontypeid), or two rows with the same id, fails the load, as confirmed on 2026-10-27; no row is skipped. The load changes nothing, so brnz_concession keeps the data from the last successful run until the source's owner corrects it and the load is run again (see the Runbook).
- **A concession type with no name is listed as 'Unnamed concession type'.** As confirmed on 2026-10-27, a type whose name is missing, empty or only spaces is still added to the concession type list, with its id, item code and flags, under the name 'Unnamed concession type', so the invoices that use it are not lost. When the source later gives it a name, the next load puts that name in place on the same id.
- **Most item codes will need mapping by hand.** As confirmed on 2026-10-27 (Q-034), the line-type mapping starts with only the 12 item codes that the existing Subs.usp_Refresh_SubsInvoices names; no other curated list exists. The first load adds every other item code, the subscription codes included, as 'unmapped'. After the first load on real data, Damian maps the unmapped codes by hand, following how Subs.usp_Refresh_SubsInvoices classifies them: a line of RIC invoice type 'SUB' whose code is in the concession product list is a concession, other 'SUB' lines are subscription, and RIC invoice type 'APP' is an enrolment or application fee. The member-year attributes use the mapping to recognise invoices that carry only an enrolment or application fee, and a line with no mapping counts as unmapped; the readmission fee check that comes later (MOD-011) also reads the line types. Under the amended specification, line types no longer affect any event amount, and 'Unmapped lines' is no longer an amount status (RULE-030). New codes that appear later arrive as 'unmapped' in the same way.
- **A wrong starting row can only be corrected by hand.** The line-type mapping load never changes an existing row, so that hand mappings are kept. The same applies to the 12 starting rows: if one is wrong, a person must correct it in the table.
- **Which spelling is stored for a new code was decided during the build.** When a new item code or currency arrives in several spellings in the same load (differing only in letter case or trailing spaces), one row is added and the same spelling is kept on every run: upper case first, then the one without trailing spaces. The design does not say which spelling to keep. Please confirm this is acceptable.
- **Two concession types could share one item code.** Nothing in the concession type list stops two live source types from carrying the same item code. The member-year attributes match the concession lines on an invoice to the concession types by item code, so such a code does not point to a single type: the load picks one of them by the concession tie-break above rather than failing. This was recorded during the build as a data risk.
- **Some concession type list behaviours were decided during the build, not by the design.** An 'rcs' prefix is removed from the product number whatever its letter case, and only at the start of the code. An item code longer than 100 characters stops the concession type list load, which changes nothing, rather than storing a cut-down code (the source product number can be up to 4,000 characters). The four starting rows (the three reserved values and 'No concession') are never changed by the load, and a type that leaves the source keeps its row in the list unchanged. Please confirm these are acceptable.
- **The new event columns are not linked to the lists by database keys.** Neither Phase 1 event table has database keys, and a key to the payment method dimension would stop the Phase 1 fact load while that dimension is empty, so none was added. The member-year attributes table does have keys to its three silver lists. The checks that every event key resolves to its dimension come with the load that fills the columns (MOD-012).
- **The fixed values the attributes load relies on are held in one place in the load.** They are the ids of Corporate (payment method), Individual and Corporate (payer type) and No concession, the first invoice year 2022 (Q-011) and the active status 'Active' (Q-027). If Q-011 or Q-027 is answered differently, that one place changes.
- **The layout of the profiles' results is not yet confirmed.** The design does not define it, and the question about it is still unanswered. The profiles were built and tested to the layout described in the Architecture and data model document. If a different layout is wanted, the procedures and their tests will need to change.
- **Some edge cases in the grain profile were decided during the build, not by the design.** Rows with no transaction type or no invoice number are not treated as invoice rows and are left out. A row with no item code adds nothing to the count of different item codes. A tax row is recognised only by the posting type 'Sales tax'. Please confirm these suit the purpose of the profile.
- **Only spaces are ignored around a payment mode code.** The mapping ignores letter case and spaces before or after a code, as confirmed on 2026-10-26. Other characters were decided during the build: a tab or a line break around a code, or a space inside it, makes the code Unrecognised. Such a code would show as Unrecognised rather than as its method. Please confirm this is acceptable.
- **The dimensions never remove a row.** This was decided during the build: the design says only that each load copies its list. An id taken out of a list would stay in its dimension (payment method, payer type, currency or concession type), because reporting data may still point to it. The payment method and payer type lists are fixed, and the currency and concession type lists never remove a row, so in practice their ids stay in place.
- **The permission script needs the analyst's role name.** The grant script uses the placeholder [<analyst_role>], because the role name is not known. It cannot be run until a person replaces the placeholder.
- **The decision records for ADR-001, ADR-003 and ADR-005 are still marked as pending**, although the design that follows their recommendations has been approved.
